核心是：唤醒词的"门控"不在服务器，而是在设备端（ESP32 固件）。 这个浏览器测试页没有设备端唤醒词检测，点开麦克风就是持续推流，服务器收到就识别的识别、该对话的对话。
     
  浏览器这边：点「录音」= 立即持续推流

  AudioRecorder.start()（test/js/core/audio/recorder.js:203）做的事就三件：

  1. 若服务器在说话，先发一条 abort（recorder.js:211）
  2. getUserMedia 打开麦克风
  3. 直接开始录音，没有任何"等唤醒词"的步骤

  推流本身是无限持续的（recorder.js:148-160）：

  processPCMBuffer(buffer) {           // 每 960 个采样
      ...
      this.websocket.send(opusData.buffer);  // 采集到就编码、就发给服务器
  }

  停止录音时也只是发一个空 opus 帧作为"我说完了"信号（recorder.js:296-299）。整个过程没有客户端唤醒词（KWS）概念，也没有 {"type":"listen","state":"start"} 之类的门控消息。

  服务器这边：唤醒词判断在 ASR 之后，不是 ASR 之前的闸门

  音频路径是：

  音频 → VAD检测人声(receiveAudioHandle.py:22)
       → ASR流式识别(asr/base.py:174)
       → startToChat() → intentHandler → checkWakeupWords(helloHandle.py:63)

  也就是说，wakeup_words 列表和 checkWakeupWords 的作用，是在语音已经被识别成文字之后判断"这第一句话是不是唤醒词"，如果是就用缓存好的快速问候语代替一次完整 LLM 调用（也就是上一轮测试里看到的"我在这里哦！/我认真听着呢，请讲。"）。它不能阻止 VAD 去识别音频 ——
  只要有人声，服务器就识别、就回答。

  真实设备为什么"先唤醒再识别"

  真实 ESP32 固件里，麦克风是一直在本地跑一个唤醒词检测模型（ESP-SR /
  醒熠等，比如识别"你好小智"），而且只有检测到唤醒词后才开始往服务器推音频。所以设备端只会在唤醒后才把声音送上来，服务器绝大多数时候收不到闲时音频。唤醒词的"第一道闸"在固件里，服务器这份唤醒词列表只是"识别后用缓存加速回应"的第二道优化。

  结论

  - 浏览器 test_page.html 是纯音频回环调试页，模拟的是"已经唤醒的设备"，没有也不打算做客户端唤醒词检测，所以任意时刻说话都会被识别并回应。
  - 这是服务器和页面当前位置下的正常行为，不是配置错误。

  如果希望浏览器页也"先等唤醒词"，有两个方向（需要的话我可以实现）：
  1. 纯前端方案：在 recorder.js 里接一个浏览器端 KWS（如 @picovoice/porcupine、onnxruntime 跑本地唤醒模型），检测到唤醒词前不推流，检测到后再 start() 推流。
  2. 服务器门控方案：给每个 connection 增加一个"未唤醒"状态，音频一律先送 VAD/KWS 识别，只有命中唤醒词才放行到 ASR/LLM —— 但这会把识别延迟和成本都转到服务端，通常不推荐。
