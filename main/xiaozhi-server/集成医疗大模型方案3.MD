# 医疗大模型（Qwen3.5-4B-Medical）+ RAGFlow 知识库 集成方案（方案三：异步并行+融合）

> 基于方案二的现有三层路由架构，核心改进：**知识库检索与医疗大模型推理异步并行执行，通用LLM融合输出**
> 知识库：RAGFlow（Docker 运行）
> 医疗 LLM：Qwen3.5-4B-Medical（外部 llama-server 部署，OpenAI 兼容接口）
> 通用 LLM：项目现有的 ChatGLM/Qwen 等（function_call 模式）

---

## 一、方案二的瓶颈

方案二（当前运行）是串行流水线：

```
Query改写(3~5s) → RAGFlow检索(10~50s) → 知识压缩(10s) → MedicalQwen推理(20~30s) → REQLLM
                                                                                     ↑
                                                                             总计: ~78s
```

两大耗时步骤 RAGFlow 检索（网络 IO 密集型）和 MedicalQwen 推理（计算密集型）**先后执行**，总耗时 = 各阶段之和。

---

## 二、方案三核心改进：异步并行 + 融合

### 2.1 并行架构

```
Query改写(3~5s)  [顺序执行，快速]
  ↓
RAGFlow健康检查（5s超时）
  │
  ├─ 健康 ─┬─ 线程A: RAGFlow检索 ──────────┐
  │         │                               │  ThreadPoolExecutor
  │         └─ 线程B: MedicalQwen推理 ──────┤  max(~30s, ~25s) = ~30s
  │                                         │
  └─ 不健康 ── 仅 MedicalQwen推理 ──────────┘
  │
  ↓
通用LLM融合（以患者问题为中心，融合两条信息源）[10~15s]
  ↓
流式TTS输出 + 安全校验
```

**总耗时变化：** 78s → 48s（节省约 37%）

### 2.2 数据流对比

```
方案二（串行）:
  用户问题 → Query改写 → RAGFlow检索 ──→ 知识压缩 ──→ MedicalQwen推理 ──→ REQLLM
                              ↓ 等待20s            ↓ 等待20s
                              时间轴: ████████████████████████████████████████ 78s

方案三（并行）:
  用户问题 → Query改写 ─┬─→ RAGFlow检索 + 压缩 ──┐
                        │                         ├─→ 通用LLM融合 ──→ 流式输出
                        └─→ MedicalQwen推理 ──────┘
                              时间轴: ████████████████████████████████ 48s
```

### 2.3 融合策略

通用 LLM 同时看到两条信息源，以患者原始问题为中心做综合：

```
【患者问题】
{question}

【知识库检索结果】
{kb_content}

【医疗模型推理结果】
{medical_answer}

请以患者问题为中心，融合以上两条信息源，给出完整、准确、有条理的回答。
如果两条信息源内容一致则合并，如果互补则综合，如果冲突则以知识库为准。
```

### 2.4 保底策略

| 场景 | 处理 |
|------|------|
| RAGFlow 健康 + MedicalQwen 成功 | 并行执行，通用 LLM 融合两者 |
| RAGFlow 健康 + MedicalQwen 失败 | 通用 LLM 仅基于 KB 回答（降级） |
| RAGFlow 不健康 + MedicalQwen 成功 | 仅 MedicalQwen 推理（跳过 KB 检索） |
| RAGFlow 不健康 + MedicalQwen 失败 | "医疗系统繁忙，请稍后再试" |

RAGFlow 健康检查（`_ragflow_health_check`）在并行执行前执行，5s 超时，避免因 RAGFlow 已挂而浪费线程池资源。

## 五、实现过程中的问题与修复

### 5.1 问题：融合结果存在但没有语音输出

**现象**：`_merge_kb_and_medical()` 成功返回了融合后的回答，但用户听不到语音。

**根因**：调用方 `receiveAudioHandle.py` 和 `connection.py` 中对 `Action.REQLLM` 的处理逻辑来自 V1：

```python
# V1 的注释 — V1 中 MedicalQwen 已经在 _call_medical_qwen 里流式输出了 TTS
# REQLLM 类型：MedicalQwen 已经在 _call_medical_qwen 中流式输出了 TTS，不重复播报
```

V2 的 `_call_medical_qwen_v2_no_stream` **不流式输出 TTS**（为了避免并行路径的 TTS 冲突），但调用方依然跳过了 TTS 播报。

**修复**：
- `receiveAudioHandle.py:154-160`：REQLLM 分支调用 `tts.tts_one_sentence()` 播报融合结果
- `connection.py:1358-1365`：REQLLM 分支调用 `self.tts.tts_one_sentence()` 播报融合结果

### 5.2 问题：`_call_medical_qwen_v2_no_stream` 使用流式接口

**现象**：函数名为 `no_stream`，但内部使用 `medical_llm.response()`（流式生成器），逐 token 循环收集结果。

**修复**：改为 `medical_llm.response_no_stream()` 非流式接口，直接获取完整回答：

```python
# 旧：流式生成器循环
full_answer = ""
for chunk in medical_llm.response("", dialogue):
    if not chunk: continue
    full_answer += chunk

# 新：非流式直接获取
full_answer = medical_llm.response_no_stream(
    system_prompt=medical_system_prompt_v2,
    user_prompt=f"【患者问题】{question}",
)
```

**效果**：代码量减少 7 行，避免生成器开销，一次 HTTP 请求直接返回。

### 5.3 问题：线程安全 — 知识库结果未被通用 LLM 压缩

**现象**：`_parallel_kb_search()` 在线程池子线程中调用 `_compress_knowledge()` → `conn.llm.response_no_stream()`，导致通用 LLM 访问静默失败，KB 结果始终为未压缩的原始文本。

**根因**：`conn.llm`（通用 LLM 客户端）不是线程安全的。在 `ThreadPoolExecutor` 的子线程中访问它，与主线程可能产生竞态。

**修复**：`_parallel_kb_search()` 只做 RAGFlow 检索 + markdown 清理，**不再调用 `_compress_knowledge()`**。原始 KB 文本由后续在主线程中执行的 `_merge_kb_and_medical()` 统一处理。

### 5.4 问题：`_merge_kb_and_medical` 中 `NameError` Bug

**现象**：函数中有以下代码，`merged` 在使用时尚未定义：

```python
# merged 在 try 块中才被赋值，但此处已引用
if kb_text and len(merged.strip()) > 20:  # NameError!
    parts.append(f"【知识库检索结果】\n{kb_text}\n")
```

**修复**：用已定义变量替代：

```python
kb_ok = kb_text and len(kb_text.strip()) > 20
med_ok = medical_text and len(medical_text.strip()) > 20
# 后续用 kb_ok / med_ok 判断
```

### 5.5 优化：融合 Prompt 精简 + 单源快速路径

**问题**：融合阶段无论是否有两条信息源，都调用 LLM。即使只有 KB 或只有 MedicalQwen 结果，也要经过一次 LLM 调用。

**优化 1 — 单源跳过 LLM 调用**：

```python
if kb_ok and not med_ok:
    return kb_text.strip()      # 直接返回，不调 LLM
if med_ok and not kb_ok:
    return medical_text.strip() # 直接返回，不调 LLM
```

**优化 2 — 提示词精简**：

| 维度 | 旧（8条） | 新（4条） | 效果 |
|------|----------|----------|------|
| 长度 | ~200 字 | ~100 字 | 首 token 延迟降低 |
| 角色 | "专业的医疗健康助手" | "腹透健康助手" | 更精准 |
| 指令 | 融合+精简+综合+冲突+分点+口语+限制思考+字数 | 综合+合并/冲突+分点+口语+字数 | 去冗余 |

**优化 3 — 参数调优**：

```python
# 旧：无参数控制
merged = conn.llm.response_no_stream(system_prompt, user_prompt)

# 新：低温度 + 上限控制
merged = conn.llm.response_no_stream(
    system_prompt, user_prompt,
    temperature=0.3,     # 更确定，输出更快
    max_tokens=1024,     # 防过度生成
)
```

### 5.7 rag检索词优化改写：由MedicalQwen 改为 通用 LLM

**问题**：`_optimize_rag_query()` 使用 MedicalQwen（本地 GPU，8106 端口）进行知识库查询改写，单次耗时 15~30s。在 V3 的并行架构中，Query 改写在主线程顺序执行，直接拖慢了整体响应时间。

```
V3 耗时分析（改前）：
  Query改写(20s) ─┬─→ RAGFlow(30s) ──┐
                    │                   ├─→ 融合(10s) = 55s
                    └─→ MedicalQwen(25s)┘
                      ↑ Query改写吃掉20s
```

**分析**：MedicalQwen 是医学微调模型，擅长医学内容生成，但**指令遵循能力弱**（常在 Query 改写时输出完整句子而非关键词），且推理速度慢。通用 LLM（如 qwen-turbo）指令遵循能力强、响应快（~3s），更适合"提取关键词"这种格式化任务。

| 维度 | MedicalQwen（旧） | 通用 LLM（新） |
|------|------------------|---------------|
| **耗时** | ~15~30s | ~2~5s |
| **指令遵循** | ⚠️ 弱 — 常输出句子而非关键词 | ✅ 强 |
| **可用性** | ⚠️ 依赖 8106 服务 | ✅ 始终可用 |
| **依赖** | `_get_medical_config()` + `create_instance()` | 零依赖，直接用 `conn.llm` |

**修复**：将 `_optimize_rag_query()` 中的 `medical_llm.response_no_stream()` 替换为 `conn.llm.response_no_stream()`，移除 MedicalQwen 的配置读取和实例化代码。

**效果**：

```
V3 耗时分析（改后）：
  Query改写(3s) ─┬─→ RAGFlow(30s) ──┐
                   │                   ├─→ 融合(10s) = 38s
                   └─→ MedicalQwen(25s)┘
                     ↑ 节省17s（31%）
```

### 5.8 新增：RAGFlow 健康检查前置

**问题**：在 V3 的并行架构中，无论 RAGFlow 是否可用，都会启动 `ThreadPoolExecutor` 提交两个任务。如果 RAGFlow 已挂，线程 A 的 `_parallel_rag_search` 会等待超时后才返回 None，浪费线程池资源且拖慢整体响应。

**解决**：在并行执行之前，先做 RAGFlow 健康检查：

```
Query改写 → RAGFlow健康检查(5s)
  ├─ 健康 → 并行: KB检索 + MedicalQwen推理
  └─ 不健康 → 仅 MedicalQwen推理
```

**新增函数**：`_ragflow_health_check(conn)`

```python
def _ragflow_health_check(conn) -> bool:
    """RAGFlow 健康检查（5s 超时）"""
    ragflow_config = conn.config.get("plugins", {}).get("search_from_ragflow", {})
    base_url = ragflow_config.get("base_url", "")
    health_url = base_url.rstrip("/") + "/api/v1/health"
    resp = requests.get(health_url, timeout=5, verify=False)
    return resp.status_code == 200
```

**流程变化**：

```
改前：Query改写 → ThreadPoolExecutor(2) → 无论RAGFlow死活都等超时
改后：Query改写 → RAGFlow健康检查 → 健康才并行，不健康只跑MedicalQwen
```

**效果**：
- RAGFlow 健康时：行为不变，并行执行两条路径
- RAGFlow 不健康时：跳过 KB 检索，只跑 MedicalQwen，避免线程池空等超时
