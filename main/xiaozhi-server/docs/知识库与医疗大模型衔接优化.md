# 知识库与医疗大模型衔接优化

> 记录 RAGFlow 知识库 → MedicalQwen 推理链路中信息丢失问题的分析与解决过程

---

## 一、问题描述

### 1.1 现状

当前腹透医疗问答的完整流水线：

```
用户端提出问题 → 拦截判断是医疗问答还是其他 → 医疗问答 → 医疗问答Query改写 → RAGFlow检索 → 知识压缩(通用LLM) → MedicalQwen推理 → 安全校验 → 发送给TTS播放 → 输出给用户端
                                   → 其他问题 → 通用LLM进行意图识别 → 插件处理 → 发送给TTS播放 → 输出给用户端
```

其中 MedicalQwen 推理环节的输入包含：
- **System Prompt**：角色设定 + 回答约束
- **User Prompt**：知识库参考内容 + 患者问题

### 1.2 问题：知识库信息被模型丢弃

MedicalQwen 在生成回答时，本质上在做"改写 + 筛选"：

```
知识库内容（完整包含 A、B、C、D 四个要点）
  + 患者问题
  → MedicalQwen 输出（只保留了 A、C、B、D 中部分丢失）
```

**根因**：模型并不知道"必须保留知识库中的所有要点"，它自然地按自己理解做了重排和裁剪。加上 MedicalQwen 上下文窗口仅 2K tokens，当知识库内容较长时，模型倾向于做摘要而非逐条覆盖。

### 1.3 影响

患者通过 TTS 收听到的回答不完整，本应从知识库获取到的正确信息被遗漏，降低了回答的准确性和可信度。

---

## 二、优化方案

### 2.1 方案设计（方案 A + B 融合）

| 方案 | 策略 | 措施 |
|------|------|------|
| **方案 A** | 优化 Prompt 强化约束 | System Prompt 新增"逐条覆盖，不得遗漏"为第一优先级 |
| **方案 B** | 结构化输出 + 可追溯 | User Prompt 要求先逐条列出 KB 全部要点，再列补充内容 |

### 2.2 System Prompt 重构

```
旧版 — 约束模糊：
  1. 直接回答用户的具体问题
  7. 【知识库优先】...以知识库为准
  → 模型可能自由筛选，不强制保留全部

新版 — 强制覆盖：
  【核心原则 — 严格遵循】
  1. 逐条覆盖知识库中的每一个要点，不得遗漏任何一条
  2. 知识库信息不足时，用医学知识补充完善
  3. 知识库内容与问题无关时，忽略它，用自身知识回答

  【回答格式】
  4. 通俗口语，分点回答（一. 二. 三.）
  5. 知识库有几个要点就列几个点，全部覆盖后再补充
```

### 2.3 User Prompt 结构化

```
旧版：
  【知识库检索资料】知识内容, 【用户原始问题】问题
  → 知识库和问题混在一起，模型不易区分

新版：
  【知识库参考内容】
  （若干条知识要点）

  【患者问题】
  （问题原文）

  回答要求：
  1. 用数字编号分点回答（1. 2. 3. ...），口语化表达
  2. 逐条列出知识库中的每一个要点，全部保留、不得遗漏
  3. 全部要点列完后，如果知识库不足以完全回答问题，额外列出补充要点
  4. 如果知识库已完整覆盖，无需补充
  5. 不要输出"一、二、"等其他标记，只用数字编号
```

### 2.4 关键设计决策

| 决策 | 原因 |
|------|------|
| **不输出中文结构标记**（一、二、） | 纯数字编号（1. 2. 3.）在 TTS 流式播报时自然流畅，无断裂感 |
| **KB 要点和补充用连续编号** | 编号连续（如 1-5 KB 要点 + 6 补充），用户感知为一条完整的清单 |
| **强化系统 Prompt 而非仅 User Prompt** | System Prompt 在整个对话中恒定，比 User Prompt 对模型行为影响更大 |

## 三、效果验证

### 3.1 优化前后对比

```
优化前：
  知识库：①低盐饮食 ②控制饮水 ③监测血压 ④定期复查
  模型输出：①低盐饮食 ③监测血压  ← ②④被丢弃

优化后：
  知识库：①低盐饮食 ②控制饮水 ③监测血压 ④定期复查
  模型输出：
    1. 低盐饮食...
    2. 控制饮水...
    3. 监测血压...
    4. 定期复查...
    5. 补充：如果出现水肿...  ← KB 全部保留 + 补充
```

### 3.2 覆盖保护机制

```
System Prompt → "不得遗漏任何一条"
User Prompt → "逐条列出每一个要点，全部保留"
输出格式 → 数字编号，先列 KB 点再补充
三重约束确保信息保全
```

## 五、Prompt 优化（第二版）

### 5.1 发现的问题

第一版优化后，实际运行发现两个问题：

| # | 问题 | 根因 |
|---|------|------|
| ① | **知识库内容未被完全覆盖** | 即使 KB 内容在 2K 上下文内，MedicalQwen 仍选择性输出 — 它把 KB 当"参考"而非"逐条复述的清单" |
| ② | **输出没有数字编号** | MedicalQwen（Qwen3.5-4B-Medical-GRPO）是**医学领域微调模型**，训练语料以段落式医学问答为主，不是指令遵循模型，无法执行"分点编号"指令 |

### 5.2 优化策略调整

```
第一版策略（失败）：
  MedicalQwen 同时做"内容生成 + 格式整理"
  → 两头不讨好，既没覆盖全，也没编号

第二版策略（正确）：
  MedicalQwen 做内容生成（它擅长的）
  → REQLLM → 通用 LLM 做格式整理（它擅长的）
```

### 5.3 System Prompt 变化

| 维度 | 第一版 | 第二版 |
|------|--------|--------|
| 角色 | 腹透健康知识问答助手 | 不变 |
| 核心原则 | 逐条覆盖，不得遗漏 | 不变 |
| **输出格式** | **分点回答，数字编号** | **连贯的段落回答** |
| **编号要求** | 有（第5条） | ❌ 移除 |
| **结束标记** | 无 | 新增 `回答结束后，另起一行输出 ===END===` |

```
第一版（要求编号）：
  5. 分点回答，每个要点用数字编号（1. 2. 3.）
  → MedicalQwen 做不到，忽略指令

第二版（段落输出）：
  5. 用连贯的段落回答，确保每个要点都被提及
  → MedicalQwen 擅长段落，输出完整
```

### 5.4 User Prompt 变化

```
第一版要求 MedicalQwen 做 5 件事：
  覆盖 KB + 编号 + 分点 + 口语 + 不用中文标记
  → 编号和分点它做不到

第二版只要求做 2 件事：
  1. 逐条覆盖 KB 要点（内容完整性）
  2. 回答结束后输出 ===END===
  → MedicalQwen 能胜任
```

### 5.5 新的数据流

```
用户问题
  → RAGFlow 检索
  → 通用 LLM 压缩（~800字）
  → MedicalQwen 段落式回答 + ===END===
  → REQLLM 传给通用 LLM
  → 通用 LLM 整理为编号分点形式
  → TTS 播报
```

## 六、RAGFlow 不可用时无输出修复（2026-07-01）

### 6.1 问题

当 RAGFlow 不可用（`ragflow_healthy = False`）时，医疗大模型单独完成检索并返回结果，但最终用户收不到任何 TTS 播报——回答文本存在，音频无输出。

### 6.2 根因

调用链路：

```
_medical_search_flow_v2()
  │ RAGFlow 不可用 → rag_result = None
  │ MedicalQwen 可用 → medical_result = "回答文本"
  │
  └─ _merge_rag_and_medical_streaming(conn, question, None, "回答文本")
       │ 第104行: if not kb_text:
       │    return medical_text   ← 直接返回，未做任何 TTS！
       │
       └─ 返回到 _medical_search_flow_v2
            │ → ActionResponse(RESPONSE, text, STREAMING_DONE_MARKER)
            │
            └─ receiveAudioHandle.py
                 → 检测到 STREAMING_DONE_MARKER → 跳过 TTS
                 → ❌ 无音频输出
```

核心问题：流式融合函数在早期返回路径（单结果）中没有做 TTS，但调用方却携带了 `STREAMING_DONE_MARKER`，导致外层认为"TTS 已在流式内部完成"而跳过。

### 6.3 修复

**文件**：`core/agentscope/fusion/fuser.py` — `_merge_rag_and_medical_streaming()`

将单结果早期返回改为**先做 TTS，再返回文本**：

```python
# 修复前：直接返回，无 TTS
if not kb_text:
    return medical_text
if not medical_text:
    return kb_text

# 修复后：先做 TTS 再返回
if not kb_text and medical_text:
    conn.tts.tts_one_sentence(conn, ContentType.TEXT, content_detail=medical_text)
    return medical_text
if not medical_text and kb_text:
    conn.tts.tts_one_sentence(conn, ContentType.TEXT, content_detail=kb_text)
    return kb_text
if not kb_text and not medical_text:
    return None
```

### 6.4 验证

| 场景 | 结果 |
|------|------|
| 仅 medical_result（RAGFlow 不可用） | ✅ TTS 被调用，输出音频 |
| 仅 kb_result（MedicalQwen 不可用） | ✅ TTS 被调用，输出音频 |
| 两者皆空 | ✅ 不调用 TTS，返回 None |
| 两者都有 | ✅ 流式融合不变 |
