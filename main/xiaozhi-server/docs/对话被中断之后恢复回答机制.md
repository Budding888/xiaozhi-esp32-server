### 问题汇总

| 问题 | 说明 | 严重程度 |
|------|------|---------|
| **答案交叉** | Q1 的天气数据（"北京市目前的天气情况如下"）完整句子混入 Q2 的医疗回答中 | **严重** |
| **句子碎片混淆** | "今天白天有雷阵雨一. 感冒了..." — 天气句子后直接拼接医疗编号，两句话被拼成一句 | **严重** |
| **逐句交织** | Q1 的天气逐日预报和 Q2 的用药建议交替出现（"周四阴首先..."、"二，气温23°到32°"） | **严重** |
| **恢复逻辑缺失** | Q1 所有内容输出完毕后，系统未询问用户是否需要继续 Q1（实际上 Q1 从未被完整回答，只是输出残留） | **中** |

### 根本原因

1. **中断后 chat(A) 未停止**：被中断后 chat(A) 的 LLM 流循环虽然跳出，但工具调用（get_weather）继续执行，结果通过 `tts_one_sentence` 写入 TTS 队列
2. **无 sentence_id 过滤**：TTS 消费者线程只检查 `client_abort`，不检查 `sentence_id`，导致 Q1 的音频帧和 Q2 的音频帧混合
3. **close 变量被后续覆盖**：`to_tts_stream` 中的 `_tts_current_sentence_id` 被 Q2 的调用覆盖，Q1 的 HTTP 响应到达时检测失效

## 二、需求

### 核心需求

| # | 需求 | 说明 |
|---|------|------|
| ① | **立即停止被中断问题的输出** | Q1 被 Q2 打断后，Q1 的残余文字/音频全部丢弃，不给用户输出 |
| ② | **记录被中断问题的原始题目** | 打断时记录 Q1 的原始问题文本 |
| ③ | **先完整回答 Q2 → 询问用户 → 确认后重答 Q1** | Q2 优先完成；结束后系统主动询问是否恢复 Q1；用户确认后从头重新完整回答 Q1 |
| ④ | **Q1 与 Q2 的作答不得混淆交织** | 两个回答在 TTS 层必须完全独立，有清晰边界 |

## 三、架构分析

### 对话处理流程

```
用户音频 → VAD 检测 → ASR 识别 → startToChat() → executor.submit(chat(text))
                                                              ↓
chat(text):                                          ThreadPoolExecutor
  ├─ dialogue.put(Message(role="user", content=text))
  ├─ LLM streaming 响应 → 逐句送入 TTS 队列
  ├─ 工具调用 → 递归 chat() (depth+1)
  └─ 结束: 送 LAST TTS 标记, 保存 assistant 到 dialogue
```

核心入口文件：`core/connection.py:chat()`

### 中断机制

中断触发路径：
- **VAD 中断**：`core/handle/receiveAudioHandle.py` — 新的语音检测触发

- **统一处理函数**：`core/handle/abortHandle.py:handleAbortMessage()`

`handleAbortMessage()` 执行的操作：
```python
async def handleAbortMessage(conn):

    conn.clear_queues()             # 清空 TTS 队列
    await conn.websocket.send(
        {"type": "tts", "state": "stop"}  # 通知客户端停止播放
```

### 关键发现 1：医疗路径绕过 chat() 的恢复漏洞

**问题**：`_direct_medical_and_speak()`、`_direct_medical_chat()`、`_agentscope_chat()` 三条医疗路由**都不经过 `chat()` 方法**。当 Q2 是医疗问题时，Q2 走医疗路径完成回答后，`chat()` 末尾的恢复询问逻辑**根本不会执行**。

```
Q1: "讲好一个故事吧" → chat() ← 被 Q2 打断
    → interrupted_queries = ["讲好一个故事吧"]

Q2: "感冒了应该怎么做" → startToChat()
    → _is_medical_query() → True
    → _direct_medical_and_speak() ← 绕过 chat()
    → Q2 回答完成 → return
    → ❌ 此处没有检查 interrupted_queries
    → 用户永远不会收到"需要继续为您解答...吗？"
```

### 关键发现 2：固定 TTS 询问被 sentence_id 过滤层丢弃

**问题**：恢复询问消息使用新生成的 `ask_sid`，但 TTS 消费者线程的过滤层要求 `message.sentence_id == conn.sentence_id`（当前为 Q2 的 sid）。新 `ask_sid` 不匹配，被丢弃，用户永远听不到询问。

```
TTS 过滤层判断:
  message.sentence_id("sid-ASK") != conn.sentence_id("sid-Q2")
  → ❌ continue → 丢弃
```

### 关键发现 3：executor.submit(chat, None) 导致 client_abort 被重置

最初尝试通过 `conn.executor.submit(self.chat, None)` 让 LLM 生成询问语句，但：
- `chat()` 入口重置 `self.client_abort = False`
- `tts_text_priority_thread` 中 `FIRST` 消息处理也重置 `self.conn.client_abort = False`
- 导致 TTS 队列中残留的 Q1 音频帧因为 `client_abort=False` 通过了过滤层
- Q1 答案与 Q2 答案交叉混杂

### 最终修复方案

**三条路径的出口统一使用「固定 TTS 提示 MIDDLE 消息」方式**：

```python
# 在所有 4 处出口（chat() 末尾 + 3 条医疗路径）统一添加：
if conn.interrupted_queries and not conn._pending_resume_query:
    next_query = conn.interrupted_queries.pop(0)
    conn._pending_resume_query = next_query
    conn._pending_resume_timeout = time.time() + 60
    ask_text = f"需要继续为您解答{next_query}的问题吗？"
    # 使用当前 conn.sentence_id 推送 MIDDLE 消息，放在现有 LAST 之前
    # 这样能通过 TTS 过滤层（因为 sentence_id 匹配），且不破坏队列边界
    conn.tts.tts_text_queue.put(
        TTSMessageDTO(
            sentence_id=conn.sentence_id,
            sentence_type=SentenceType.MIDDLE,
            content_type=ContentType.TEXT,
            content_detail=ask_text,
        )
    )
```

**关键要点**：
1. 使用**当前 `conn.sentence_id`**（Q2 的 sid）推送，通过 sentence_id 过滤层
2. 只推送一条 **MIDDLE** 消息，插在现有 LAST 之前，不额外创建 FIRST/LAST 边界
3. **不调用 `chat()`**，不重置 `client_abort`

**最终 TTS 队列顺序**（Q2 末尾 → 恢复询问）：
```
[MIDDLE(Q2-内容)] [MIDDLE(Q2-内容)] [MIDDLE(免责声明)] [MIDDLE(需要继续为您解答...)] [LAST(Q2)]
   └────────── Q2 完整的 sentence ──────────┴────── 恢复询问 ───┘
```

**等待时间**：恢复 MIDDLE 与 LAST 之间无额外延时。用户从 Q2 内容播完到听到询问声，等待时间 = `_send_disclaimer_tts` 的 TTS 合成时间（1-2 秒）+ `time.sleep(1)`（免责声明内的停顿）= **约 2-3 秒**。

| 路径 | 文件 | 插入位置 |
|------|------|---------|
| `_direct_medical_and_speak` | `core/handle/receiveAudioHandle.py` | LAST 之前 |
| `_direct_medical_chat` | `core/connection.py` | LAST 发送之后，return 之前 |
| `_agentscope_chat` | `core/connection.py` | LAST 发送之后，return 之前 |
| `chat()` 末尾 | `core/connection.py` | dialogue 清理之后，return 之前 |

```python
async def handleAbortMessage(conn: "ConnectionHandler"):
    if conn.close_after_chat or conn.is_exiting:
        conn.logger.bind(tag=TAG).info("退出流程中被打断，直接关闭连接")
        return

    conn.logger.bind(tag=TAG).info("Abort message received")

        conn.interrupted_queries.append(conn.current_query)

        )
    else:
        conn.logger.bind(tag=TAG).debug("current_query 为空，跳过保存")

    conn.client_abort = True
    conn.clear_queues()
    await conn.websocket.send(
        json.dumps({"type": "tts", "state": "stop", "session_id": conn.session_id})
    )
    conn.clearSpeakStatus()
```

### Task 4: chat() 方法 5 个保护点

**文件**: `core/connection.py:chat()`

| # | 保护点 | 位置 | 代码 |
|---|--------|------|------|
| ① | 入口跟踪 | depth==0 | `self.current_query = query; self._chat_was_aborted = False` |
| ② | 中断标记 | LLM 流循环 | `if self.client_abort: self._chat_was_aborted = True; break` |
| ③ | 跳过工具调用 | tool_call_flag | `if tool_call_flag **and not self._chat_was_aborted:**` |
| ④ | 跳过不完整保存 | response_message | `if ... **and not self._chat_was_aborted:**` |
| ⑤ | 跳过僵尸 LAST | depth==0 | `if depth == 0 **and not self._chat_was_aborted:**` |

**为什么需要跳过工具调用？**：
被中断的 chat(A) 中 LLM 已经生成了工具调用请求。如果继续执行：
1. `future.result(timeout=30)` 会阻塞等待最长 30 秒
2. 工具调用的结果通过 `tts_one_sentence` 写入 TTS 队列
3. chat(B) 也在向同一队列写入 → 内容交叉

**为什么要跳过 LAST 标记？**：
```
没有跳过时的错误时序：
  [FIRST(B)] [LAST(A_zombie)] [MIDDLE(B)] ... [LAST(B)]
       ↑                             ↑
   B 刚被 FIRST 开始     TTS 消费者看到 LAST(A) 以为句子结束了
                        B 真正的 MIDDLE 内容与 A_resumed 的 FIRST 混在一起

正确时序：
  [FIRST(B)] [MIDDLE(B)] ... [LAST(B)] [FIRST(Ar)] [MIDDLE(Ar)] ... [LAST(Ar)]
  ───────── B 完全独立 ──────  ──────── A_resumed 完全独立 ──────────
```

### Task 5: 用户确认恢复机制（核心需求）

**文件**: `core/connection.py` — 3 个新方法 + chat() 入口/末尾修改 + 固定 TTS 询问

#### 5a: 新增 3 个方法

```python
def _is_user_confirming(self, user_input: str, pending_query: str) -> bool:
    """判断用户是否确认恢复（关键词匹配 + 确认词）"""
    # 规则1：用户输入包含原问题的关键词 → 视为确认
    keywords = self._extract_keywords(pending_query)
    if any(kw in user_input for kw in keywords):
        return True
    # 规则2：包含确认词（继续/好的/是的）且不含拒绝词 → 视为确认
    confirm_words = ["继续", "好的", "是的", "对", "嗯", "好", "可以", "要"]
    refuse_words = ["不用", "不要", "不了", "算了", "跳过", "别"]
    has_confirm = any(cw in user_input for cw in confirm_words)
    has_refuse = any(rw in user_input for rw in refuse_words)
    return has_confirm and not has_refuse

def _is_user_refusing(self, user_input: str, pending_query: str) -> bool:
    """判断用户是否拒绝恢复（不用/不要/算了/跳过）"""
    refuse_words = ["不用", "不要", "不了", "不", "算了", "跳过", "没"]
    return any(rw in user_input.strip() for rw in refuse_words)

def _extract_keywords(self, text: str) -> list:
    """从问题中提取关键词（移除标点/疑问词，保留核心名词）"""
    import re
    cleaned = re.sub(r'[吗呢啊吧呀么么什哪谁啥的得了着过是]', '', text)
    cleaned = re.sub(r'[？?！!。，、；：""''【】《》（）\s]', '', cleaned)
    words = [w.strip() for w in re.split(r'[,，\s]+', cleaned) if w.strip() and len(w) >= 2]
    return words if words else [text[:8]]
```

### Task 6: TTS 层 8 级过滤保护

**文件**: `core/providers/tts/base.py`

#### 6a: 闭包捕获 retained_sid

```python
def to_tts_stream(self, text, opus_handler=None):
    # 闭包捕获当前 sentence_id（快照值，不可被后续覆盖）
    retained_sid = getattr(self.conn, 'sentence_id', None) if self.conn else None

    def _is_stale():
        if retained_sid is not None:
            current_sid = getattr(self.conn, 'sentence_id', None)
            if current_sid is not None and retained_sid != current_sid:
                return True
        if getattr(self.conn, 'client_abort', False):
            return True
        return False

    def _make_filtered_opus(original_handler, expected_sid):
        def _wrapped(data):
            if expected_sid is not None:
                current_sid = getattr(self.conn, 'sentence_id', None)
                if current_sid is not None and expected_sid != current_sid:
                    return  # 丢弃残留音频帧
            if getattr(self.conn, 'client_abort', False):
                return
            original_handler(data)
        return _wrapped
```

#### 6b: 音频队列 3→4 字段

所有 `tts_audio_queue.put()` 调用从 `(type, data, text)` 扩展为 `(type, data, text, sentence_id)`。

#### 6c: sentence_id 过滤

`_audio_play_priority_thread` 和 `tts_text_priority_thread` 中添加过滤：
```python
if sentence_id is not None:
    current_sid = getattr(self.conn, 'sentence_id', None)
    if current_sid is not None and sentence_id != current_sid:
        logger.debug(f"丢弃残留消息(sid={sentence_id})")
        continue
```

#### 完整 8 级过滤体系

| 层级 | 位置 | 过滤依据 | 防护范围 |
|------|------|---------|---------|
| ① | chat() 跳过工具调用 | `_chat_was_aborted` | 阻止被中断 chat 写入 TTS |
| ② | chat() 跳过不完整保存 | `_chat_was_aborted` | 阻止污染对话历史 |
| ③ | chat() 跳过僵尸 LAST | `_chat_was_aborted` | 阻止干扰 TTS 队列边界 |
| ④ | `_is_stale()` | 闭包 `retained_sid` | 阻断合成层残留（闭包不可覆盖） |
| ⑤ | `filtered_opus` 回调 | 闭包 `expected_sid` | 阻断音频帧入队前 |
| ⑥ | `tts_text_priority_thread` | `message.sentence_id` | 丢弃残留 TTS 文本消息 |
| ⑦ | `_audio_play_priority_thread` | `sentence_id` 字段 | 丢弃音频队列中残留 |
| ⑧ | `clear_queues()` | 无条件清空 | 确保打断时队列干净 |

#### 7a: `_ensure_sending()` 方法

```python
def _ensure_sending(self):
    """检测发送循环是否存活，若死则自动重启"""
    if not getattr(self, '_send_callback', None):
        return
    task_alive = (hasattr(self, 'pending_send_task')
                  and self.pending_send_task is not None
                  and not self.pending_send_task.done())
    if not task_alive:
        if loop.is_running():
            self.pending_send_task = asyncio.create_task(self._run_send_loop())
```

#### 7b: `_run_send_loop()` 异常容错

```python
async def _run_send_loop(self):
    while True:
        try:
            await self.queue_has_data_event.wait()
            await self.check_queue(self._send_callback)
        except asyncio.CancelledError:
            break  # 主动取消退出
        except Exception as e:
            continue  # 异常恢复
```

## 八、故障排除

### 答案交叉

如果仍然出现答案交叉，可能原因及排查方式：

| 现象 | 可能原因 | 排查方式 |
|------|---------|---------|
| Q1 内容混入 Q2 | TTS 文本消息层缺少 sentence_id 过滤 | 确认 tts_text_priority_thread 中已添加 sentence_id 匹配检查 |
| 状态消息混入回答 | LLM 流式分块 + 工具调用的 tts_one_sentence 同时写入队列 | 检查 TTS 队列中消息的 sentence_id 是否一致 |
| 恢复回答包含 Q2 上下文 | 对话历史中 Q2 的 exchange 被 LLM 引用 | 正常行为，LLM 需要上下文来理解问题 |

### 用户确认问题

| 现象 | 可能原因 | 排查方式 |
|------|---------|---------|
| 用户确认后不恢复 | `_is_user_confirming` 未匹配到用户输入 | 检查 extract_keywords 提取结果；检查日志中"用户确认恢复问题" |
| 用户未确认但触发了恢复 | `_is_user_confirming` 误判 | 检查拒绝词匹配逻辑 |
| 询问后用户长时间无回应 | 60 秒超时自动放弃 | 确认日志中"恢复确认超时" |
| 恢复回答不完整 | LLM 未看到完整 Q1 上下文 | 检查 dialogue 中是否保留了 Q1 的用户消息 |
