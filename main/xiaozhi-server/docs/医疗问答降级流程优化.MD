# 腹透医疗问答降级流程优化

## 一、问题分析

### 1.1 当前架构

```
用户提问 → _is_medical_query() 关键词拦截
  → search_medical_question()
      ├─ Query改写（调用 MedicalQwen 8106）
      ├─ RAGFlow知识库检索（8008）
      ├─ 知识库压缩（通用LLM）
      ├─ MedicalQwen推理（调用 MedicalQwen 8106）
      └─ 医疗内容安全校验 → 返回通用LLM润色
```

### 1.2 五个问题

| # | 问题 | 影响 |
|---|------|------|
| ① | **无服务健康检查**：`search_medical_question` 启动后第一步就调用 MedicalQwen，没有前置探针 | 如果 8106 已挂，第一步 Query改写就等待60s超时才降级 |
| ② | **乐观进度播报误导用户**：`"抱歉，让您久等了。本次查询到的结果汇总如下"` 在获得 `_call_medical_qwen` 结果 **之前** 发送 | 用户听完以为有结果，紧接着听到"医疗系统繁忙"，体验极差 |
| ③ | **长超时等待**：MedicalQwen Provider `timeout=60`，服务挂掉时需等满60s才报错 | 整条流水线耗时 60~120s 后只返回一个错误 |
| ④ | **免责声明追加到错误消息**：`receiveAudioHandle.py` 的 `_direct_medical_and_speak()` 始终在末尾追加免责声明 | 错误消息"医疗系统繁忙" + 免责声明，听起来像真实医疗回答 |
| ⑤ | **无智能降级**：RAGFlow 有结果时也被丢弃，直接返回"医疗系统繁忙" | 知识库中已有的信息无法触达用户 |

### 1.3 用户完整等待时间线（8106 挂掉时）

```
[0s]   用户：   "腹透患者感冒了应该吃什么药"
[1s]   机器人： "好的。"
[2s]   机器人： "正在为查询关于腹透患者感冒了应该吃什么药有关的回答，请稍候。"
[3s]   机器人： "正在检索知识库。"
        （开始 Query改写 → 调8106 → 等待60s超时）
[63s]   （Query改写失败，降级为原始问题）
        （RAGFlow检索，可能成功也可能失败）
        （开始 MedicalQwen推理 → 调8106 → 等待60s超时）
[123s]  机器人： "抱歉，让您久等了。本次查询到的结果汇总如下。"  ← 实际上无结果
[124s]  机器人： "医疗系统繁忙，请稍后再试"
[125s]  机器人： "温馨提示：以上内容仅供参考..."  ← 用户以为这是回答
```

## 二、优化方案（C 方案：完整降级架构重构）

### 2.1 架构变更

```
                    ┌─────────────────────────────────┐
                    │    search_medical_question()      │
                    │    ┌─────────────────────────┐    │
                    │    │  Step 0: 健康检查          │    │
                    │    │  LLMProvider.health_check() │    │
                    │    │  超时 5s，缓存 30s          │    │
                    │    └──────────┬──────────────┘    │
                    └──────────────┼────────────────────┘
                                   │
                    ┌──────────────┴──────────────┐
                    ▼ (健康)                       ▼ (不健康)
        ┌──────────────────────┐       ┌──────────────────────┐
        │ Level 0               │       │ 降级路径               │
        │ _normal_medical_flow   │       │ _fallback_medical_flow │
        │ (完整流水线，不变)      │       │ (跳过 Query改写)       │
        │                       │       │                      │
        │ 1. Query改写           │       │ 1. RAGFlow检索        │
        │ 2. RAGFlow检索         │       │    ├─ 有结果 → Level 1│
        │ 3. 知识压缩(通用LLM)    │       │    └─ 无结果 → Level 2│
        │ 4. MedicalQwen推理     │       │ 2. 通用LLM回答        │
        │ 5. 安全校验             │       │ 3. 安全校验            │
        │ 6. 返回 REQLLM         │       │ 4. 返回 RESPONSE      │
        └──────────────────────┘       └──────────────────────┘
```

### 2.2 四级降级策略

| 级别 | 条件 | 行为 | 响应类型 |
|------|------|------|---------|
| **Level 0** | MedicalQwen 健康 | 完整流水线：Query改写 → RAGFlow → MedicalQwen → 校验 | `Action.REQLLM` → 通用LLM润色 |
| **Level 1** | MedicalQwen 不健康 + RAGFlow有结果 | 通用LLM 基于 RAGFlow 结果整理回答 | `Action.RESPONSE` → 直接TTS |
| **Level 2** | MedicalQwen 不健康 + RAGFlow无结果 | 通用LLM 基于自身医学知识回答 | `Action.RESPONSE` → 直接TTS |
| **Level 3** | 通用LLM 也失败 | "医疗系统繁忙，请稍后再试" | `Action.RESPONSE` → 直接TTS |

### 2.3 进度播报时序修正

| 阶段 | 旧播报 | 新播报 |
|------|--------|--------|
| 入口 | "正在为查询关于{问题}有关的回答" | "好的，正在为您查询" |
| RAGFlow中 | "正在检索知识库" | "正在检索知识库" |
| ⇒ Level 0 | "抱歉，让您久等了。本次查询到的结果汇总如下" | "已为您查询到以下医疗信息" |
| ⇒ Level 1 | （无此路径） | "已查询到相关知识，正在整理回答" |
| ⇒ Level 2 | （无此路径） | "正在为您解答，请稍候" |
| ⇒ Level 3 | （直接错误） | （无进度播报，直接报错） |

核心原则：**"已经查到结果"类消息只在确认有结果后播放。**

### 2.4 文件修改范围

| 文件 | 改动量 | 内容 |
|------|--------|------|
| `core/providers/llm/medical_qwen/medical_qwen.py` | ~45行新增 | 新增 `health_check()` 类方法（`GET {base}/health`，5s超时 + 30s缓存） |
| `plugins_func/functions/search_medical_question.py` | ~150行重构 | 拆分为 `_normal_medical_flow` + `_fallback_medical_flow`，新增 `_fallback_answer_with_llm` |
| `core/handle/receiveAudioHandle.py` | ~15行修改 | 移除重复免责声明（`_medical_verify` 已内联追加，避免用户听到两遍） |
| `core/connection.py` | ~5行修改 | 移除 `_direct_medical_chat` 中 REQLLM 路径的重复 TTS 播报（已在 `_call_medical_qwen` 中流式输出） |

## 三、代码审查与修复

实现完成后使用 `code-reviewer` agent 进行了代码审查，发现并修复以下问题：

### 3.1 HIGH 严重度修复

| # | 问题 | 根因 | 修复 |
|---|------|------|------|
| ① | **双重免责声明** | `_medical_verify()` 将免责声明内联追加到回答文本中；同时 `_direct_medical_and_speak()` 又作为独立 TTS 消息追加一次 | 移除 `_direct_medical_and_speak()` 中的独立免责声明，由 `_medical_verify()` 统一处理 |
| ② | **双重 TTS 回答播报** | `_call_medical_qwen()` 已通过流式方式将每个 token 送入 TTS 队列；但 `_direct_medical_chat()` 的 REQLLM 分支又调用 `tts.tts_one_sentence()` 重播完整回答 | 移除 `_direct_medical_chat()` REQLLM 分支的 `tts.tts_one_sentence()` 调用，与 `_direct_medical_and_speak()` 行为一致 |

### 3.2 MEDIUM 修复

| # | 问题 | 修复 |
|---|------|------|
| ① | `_compress_knowledge()` 中压缩成功日志使用了 `logger.warning()` 级别 | 改为 `logger.info()` |
| ② | `_query_knowledge_base()` 中注释"如果整理压缩后的长度小于原始长度，则返回压缩后的结果"与实际代码逻辑不符 | 修正为"压缩失败或未执行，返回原始知识文本" |

### 3.3 最终文件清单

| 文件 | 最终改动量 | 说明 |
|------|-----------|------|
| `core/providers/llm/medical_qwen/medical_qwen.py` | +45行 | 新增 `health_check()` 类方法（`GET {base}/health` 接口） |
| `plugins_func/functions/search_medical_question.py` | ~150行重构 | 多级降级架构 + 共享配置函数 |
| `core/handle/receiveAudioHandle.py` | ~10行修改 | 移除重复免责声明 |
| `core/connection.py` | ~3行修改 | 移除重复 TTS 播报 |
