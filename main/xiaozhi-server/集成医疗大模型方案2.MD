# 医疗大模型（Qwen3.5-4B-Medical）+ RAGFlow 知识库 集成方案（方案二：现状）

> 基于 xiaozhi-esp32-server 现有架构，**双层关键词拦截 + 三阶段处理管线**
> 这是项目中**当前使用并运行**的集成方案。
> 知识库：RAGFlow（Docker 运行，通过 `search_from_ragflow` 插件查询）
> 医疗 LLM：Qwen3.5-4B-Medical（外部项目 AutoTokenizer 部署，OpenAI 兼容接口）
> 通用 LLM：项目现有的 ChatGLM/Qwen 等（function_call 模式）

---

## 一、方案二的演进背景

方案一（纯 function_call 方案）在部署后暴露了两个关键问题：

| 问题 | 现象                                              | 根因 |
|------|-------------------------------------------------|------|
| **时序竞争** | 消息先于初始化完成到达，预过滤器被跳过，始终走通用 LLM。有时触发了通用LLM，有时候触发了知识库，但是根本没有出发医疗大模型                  | `chat()` 内部依赖 `intent_type`、`func_handler` 等初始化状态，异步初始化可能导致条件不满足 |
| **LLM 偷懒** | LLM 认为腹透问答属于"通用知识问答"，即使工具列表中有 `search_medical_question` 也不调用 | `TOOL_CALLING_RULES` 中的 "通用知识问答不调工具" 规则与医疗需求冲突 |

**方案二的核心改进：** 添加**入口级关键词拦截层**作为医疗路由的最高优先级保障，形成**入口拦截 → LLM 内预过滤 → LLM function_call** 三层兜底机制，彻底解决时序依赖和 LLM 决策不可靠问题。

## 二、整体架构（三层路由）

```
用户文本输入
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ Layer 1: 入口预过滤器（receiveAudioHandle.py）        │
│ 位置: startToChat() 最开头，在意图分析之前            │
│ 条件: hasattr(conn, '_is_medical_query') 仅依赖 conn   │
│ 命中: → _direct_medical_and_speak() → 直接 TTS 输出   │
│ 不命中: → 继续往下                                    │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ Layer 2: 意图分析 + LLM function_call                  │
│ handle_user_intent() → intentHandler                   │
│ LLM 看到 tool list 中有 search_medical_question                     │
│ 根据描述决定是否调用                                   │
└──────────────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────────────┐
│ Layer 3: chat() 内预过滤器（connection.py）            │
│ 位置: chat() 最开头，depth==0 时                      │
│ 条件: intent_type=="function_call" AND has_tool("search_medical_question") AND 关键词命中  │
│ 命中: → _direct_medical_chat() → TTS 输出              │
│ 不命中: → 常规 LLM 对话                                │
└──────────────────────────────────────────────────────┘
```

### 三层兜底的关系

| 层 | 位置 | 依赖条件 | 可靠性 | 作用 |
|----|------|---------|--------|------|
| Layer 1 | `startToChat()` 入口 | 仅依赖 `conn._is_medical_query()` | ✅ 最高 | 即使其他组件未初始化也能拦截 |
| Layer 2 | LLM function_call | LLM 正确理解工具描述 | ⚠️ 依赖模型 | 覆盖 Layer 1/3 关键词未覆盖的边缘情况 |
| Layer 3 | `chat()` 内预过滤 | intent_type + has_tool + 关键词 | ✅ 高 | 在 function_call 路径中保障二层拦截 |

**三种路径中任意一条命中，医疗问题都会被路由到 `search_medical_question` 插件。**

## 三、完整数据流

### 场景 1：入口拦截（最常见路径 — 医疗问题）

```
用户: "腹膜炎的并发症有哪些？"
    │
    ▼
startToChat()
    │
    ├─ Layer 1: conn._is_medical_query("腹膜炎的并发症有哪些？")
    │   → 命中关键词: "腹膜炎"、"并发症" ✅
    │
    └─ _direct_medical_and_speak(conn, text)  ← 在线程池中执行
        │
        ├─ TTS FIRST 标记
        ├─ search_medical_question(conn, question=text)
        │   │
        │   ├─ Step 0: 健康检查（MedicalQwen 是否存活）
        │   │   → GET {base}/health（5s超时，30s缓存）
        │   │   → 健康 → Level 0 正常流水线
        │   │   → 不健康 → 进入降级路径
        │   │
        │   ├─ [Level 0] 正常流水线:
        │   │   ├─ 1.Query改写（MedicalQwen 优化检索关键词）
        │   │   ├─ 2.RAGFlow 知识库检索（search_from_ragflow_v2）
        │   │   │  → 相似度过滤 → 内容去重 → 长度截断（3000字）
        
        │   │   ├─ 3.知识压缩（通用 LLM 整理为 ~800 字摘要）
        │   │   ├─ 构建 Prompt
        │   │   │  system: 腹透健康助手（逐条覆盖+段落输出）
        │   │   │  user: 【知识库参考内容】+【患者问题】+ 回答要求
        
        │   │   ├─ 4.调用 MedicalQwen Provider（流式输出）
        │   │   │  → 逐 chunk 送入 TTS 队列
        │   │   │  → 回答结束后输出 ===END=== 标记
        
        │   │   ├─ 5.医疗内容安全校验（禁忌词替换 83 项）
        │   │   └─ 6.返回 ActionResponse(Action.REQLLM, result, None)
        │   │
        │   ├─ [Level 1/2] 降级路径（MedicalQwen 不可用）:
        │   │   ├─ 直接查 RAGFlow（跳过 Query 改写）
        │   │   ├─ Level 1: RAGFlow有结果 → 通用 LLM 基于 KB 整理回答
        │   │   └─ Level 2: RAGFlow无结果 → 通用 LLM 基于自身知识回答
        │   │
        │   └─ [Level 3] 全部不可用 → "医疗系统繁忙，请稍后再试"
        │
        ├─ （非错误时）发送免责声明（独立 TTS，停顿 1 秒后播报）
        ├─ TTS LAST 标记
        └─ 记录对话到 conn.dialogue

    结果: TTS 直接播报 → return，完全不经过 intentHandler/chat()

    注: REQLLM 返回的 MedicalQwen 段落式回答，会由通用 LLM 在后续
    对话轮次中整理为编号分点形式，由通用 LLM 输出最终格式化答案。
```

### 场景 2：LLM function_call 触发（Layer 1/3 未命中，但 LLM 识别出医疗问题）

```
用户: "我最近总是头晕，是什么原因？"
    │
    startToChat()
    ├─ Layer 1: _is_medical_query("我最近总是头晕，是什么原因？")
    │   → 命中 "头晕" ✅ → 走 Layer 1 拦截
    │
    或（关键词未覆盖时）:
    ├─ Layer 1: 未命中 → handle_user_intent() → 通用 LLM function_call
    │   → LLM 查看工具列表，search_medical_question 描述匹配"体征咨询"
    │   → 调用 search_medical_question  → 三阶段处理管线
    └─ Layer 3: chat() 内预过滤器 → _direct_medical_chat()
```

### 场景 3：非医疗问题（不走医疗通道）

```
用户: "今天天气怎么样？"
    │
    startToChat()
    ├─ Layer 1: _is_medical_query → 未命中任何关键词 ❌
    ├─ Layer 2: handle_user_intent() → 通用 LLM
    │   → search_medical_question 描述不匹配 → 调 get_weather 工具
    └─ Layer 3: chat() 内预过滤器 → 关键词不匹配 → 常规 LLM 回答
```

### 场景 4：RAGFlow 不可用时降级

```
正常流水线（MedicalQwen 健康时）:
  search_medical_question 执行:
    ├─ Step 1: Query改写（MedicalQwen 改写检索关键词）
    ├─ Step 2: search_from_ragflow_v2 FAIL
    │   → knowledge_context = ""（空）
    ├─ Step 3: 压缩跳过（无内容）
    │
    └─ MedicalQwen 直接基于自身知识推理

        → 禁忌词替换 → REQLLM 返回
```

### 场景 5：MedicalQwen 不可用时降级（四级降级）

```
search_medical_question 执行:
    ├─ Step 0: 健康检查 → 5s 超时 → 不可用 ❌
    │
    └─ 进入降级路径:
        ├─ Level 1: RAGFlow有结果 → 通用 LLM 基于 KB 整理回答 ✅
        ├─ Level 2: RAGFlow无结果 → 通用 LLM 基于自身知识回答 ✅
        └─ Level 3: 通用 LLM 也失败 → "医疗系统繁忙，请稍后再试"
```

## 四、医疗关键词体系（`_is_medical_query`）

定义在 `core/connection.py:1213`，30+ 腹透医疗关键词，分 6 大类：

| 类别 | 关键词 |
|------|--------|
| 腹透相关 | 腹透、腹膜透析、透析、腹膜炎、腹透液、透析液、出口感染、管路、换液、换药、碘伏帽 |
| 并发症 | 并发症、感染、发炎 |
| 饮食营养 | 饮食、吃什么、忌口、食谱、三餐、营养、蛋白质、饮水量、喝水、水分、钾、磷、钠、盐 |
| 体征 | 血压、血糖、体重、尿量、水肿、超滤、干体重、腹围 |
| 药物 | 吃药、用药、药物、药、禁忌 |
| 护理/症状 | 护理、注意、怎么、如何、肚子痛、腹痛、发热、发烧、呕吐、恶心、头晕、乏力、肿胀 |

### 排除机制（防止误拦截）

医疗预过滤器在关键词匹配之前先执行两道排除逻辑，确保体征数据上报/更新类问题不被误拦截：

**排除模式1 — 体征数据上报/记录/查询：**

当查询**同时包含**体征测量词和上报操作词时，判定为数据上报意图，不走医疗通道，交由通用 LLM 的 function_call 路由到对应插件。

| 体征测量词 | 上报操作词 |
|-----------|-----------|
| 血压、血糖、体重、尿量、心率 | 上报、提交、记录、录入、查询、查一下、查查 |

**边界示例：**

| 用户输入 | 是否排除 | 预期路由 |
|----------|---------|---------|
| "上报血压150/90" | ✅ 排除 | `submit_blood_pressure_data` |
| "体重65公斤请上报" | ✅ 排除 | `submit_weight_data` |
| "记录血糖5.6" | ✅ 排除 | `submit_blood_glucose_data` |
| "查询我的血压" | ✅ 排除 | LLM function_call 路由 |
| "血压高怎么办？" | ❌ 不排除 | `search_medical_question` ✅ |
| "血糖正常范围是多少" | ❌ 不排除 | `search_medical_question` ✅ |
| "我最近体重增加" | ❌ 不排除 | `search_medical_question` ✅ |

**排除模式2 — 服药提醒更新：**

当查询包含"更新" + "提醒/服药/用药提醒"时，排除不走医疗通道。

| 用户输入 | 是否排除 | 预期路由 |
|---------|---------|---------|
| "更新服药提醒" | ✅ 排除 | `update_medication_reminder_status` |
| "帮我更新一下用药提醒" | ✅ 排除 | `update_medication_reminder_status` |

## 六、核心文件详解

### 6.1 MedicalQwen Provider

**路径：** `core/providers/llm/medical_qwen/medical_qwen.py`

- 继承 `LLMProviderBase`，实现 `response()`（流式）和 `response_no_stream()`（非流式）
- 对接外部项目通过 `AutoTokenizer.from_pretrained` 部署的服务
- 接口格式：OpenAI 兼容 `/v1/chat/completions`
- 支持实时流式输出，逐 token 送入 TTS 队列

```python
class LLMProvider(LLMProviderBase):
    def __init__(self, config):
        self.base_url = config.get("base_url", "http://localhost:8101/v1")
        self.client = OpenAI(api_key=..., base_url=..., timeout=...)

    def response(self, session_id, dialogue, **kwargs):
        """流式响应 — 供 TTS 实时播报"""
        yield content  # 逐 token

    def response_no_stream(self, system_prompt, user_prompt, **kwargs):
        """非流式响应 — 供内部调用"""
        return answer
```

**工厂实例化：** `core/utils/llm.py` 通过 `create_instance("medical_qwen", config)` 自动发现并创建实例。

### 6.2 Medical QA 插件

**路径：** `plugins_func/functions/search_medical_question.py`

这是**医疗问答的编排核心**，被三种路径调用（入口拦截、预过滤器、LLM function_call）。

**五阶段处理管线（Level 0 正常流水线）：**

```
search_medical_question(conn, question)
    │
    ├── Stage 0: 健康检查
    │   GET {base}/health（5s 超时，30s 缓存）
    │   → 健康 → Level 0 正常流水线
    │   → 不健康 → 进入降级路径（Level 1/2/3）
    │
    ├── Stage 1: Query 改写 + RAGFlow 检索
    │   _optimize_rag_query() → MedicalQwen 改写口语化为关键词
    │   search_from_ragflow_v2() → 多阶段过滤：
    │     相似度阈值→内容去重→top8→3000字截断
    │   _strip_ragflow_markdown() → 清理 markdown 格式
    │   _compress_knowledge() → 通用 LLM 压缩为 ~800 字摘要
    │
    ├── Stage 2: 构建 Prompt + MedicalQwen 推理
    │   system: medical_system_prompt（腹透健康助手，段落输出）
    │   user: 【知识库参考内容】{context} 【患者问题】{question}
    │   → 流式输出，逐 chunk 送入 TTS 队列
    │   → 回答结束后输出 ===END=== 标记
    │
    ├── Stage 3: 内容安全校验
    │   → 禁忌词替换（83 项，覆盖饮水/饮食/用药/透析/监测等）
    │   → 返回 ActionResponse(Action.REQLLM, text, None)
    │
    └── Stage 4: 输出后处理（在 caller 中完成）
        → 通用 LLM 将段落整理为编号分点形式（通过 REQLLM）
        → 免责声明作为独立 TTS 消息（停顿 1 秒后播报）
```

**降级路径（MedicalQwen 不可用）：**

```
_fallback_medical_flow(conn, question):
    ├─ Level 1: RAGFlow有结果 → 通用 LLM 基于 KB 回答
    ├─ Level 2: RAGFlow无结果 → 通用 LLM 基于自身知识回答
    └─ Level 3: 通用 LLM 失败 → "医疗系统繁忙，请稍后再试"
```

**关键设计决策：**
1. **健康检查前置**：Stage 0 用 `GET {base}/health`（5s 超时）快速判断服务状态，避免无谓等待 60s
2. **四级降级**：MedicalQwen 不可用时依次降级到通用 LLM + RAGFlow → 通用 LLM 自身知识 → 错误消息，不再直接报错
3. **流式 TTS 输出**：MedicalQwen 逐 token 实时送入 TTS 队列，实现"边推理边播报"
4. **MedicalQwen 做内容、通用 LLM 做格式**：MedicalQwen 输出连贯段落（它擅长的），通用 LLM 在 REQLLM 阶段整理为编号分点（它擅长的）
5. **禁忌词 83 项**：覆盖饮水、饮食、药物、透析、监测、感染、活动、症状 8 大类
6. **免责声明独立 TTS**：不作为文本追加，而是以独立 TTS 消息发送，停顿 1 秒后播报，不与主回答紧贴

### 6.4 入口拦截层

**路径：** `core/handle/receiveAudioHandle.py`

在 `startToChat()` 函数最开头，意图分析之前插入医疗拦截：

```python
# ===== 医疗入口预过滤器（最高优先级） =====
if hasattr(conn, '_is_medical_query') and conn._is_medical_query(actual_text):
    conn.executor.submit(_direct_medical_and_speak, conn, actual_text)
    return
```

`_direct_medical_and_speak()` 在线程池中执行完整的医疗问答流程，包括 TTS 的 FIRST/LAST 标记管理和对话记录。

### 6.5 聊天内预过滤器

**路径：** `core/connection.py`

在 `chat()` 函数开头（`depth==0` 时），作为 Layer 3 兜底：

```python
if (depth == 0 and query is not None
    and self.intent_type == "function_call"
    and self.func_handler.has_tool("search_medical_question")
    and self._is_medical_query(query)):
    return self._direct_medical_chat(query)
```

`_direct_medical_chat()` 直接调用 `search_medical_question` 插件并处理 TTS 输出和对话记录。

## 七、异常降级链

```
User Input → search_medical_question 调用
```

## 十一、优化迭代记录

### 11.1 RAGFlow 检索质量优化（方案1 + 方案2）

**问题：** 患者询问腹透相关问题时，RAGFlow 知识库返回的结果零散、相关度不高，MedicalQwen 基于这样的上下文生成回答，效果不理想。

**根因分析：**
1. RAGFlow 检索参数未调优（默认 `top_k` 小，无相似度阈值过滤）
2. 患者口语化问题（"腹透要注意什么？"）直接做向量检索，命中率低

**优化方案（双层优化）：**

#### 方案1：RAGFlow 检索参数调优

在 `search_from_ragflow.py` 和 `config.yaml` 中新增检索参数：

```yaml
search_from_ragflow:
  top_k: 8                    # 召回候选数从默认增大到8
  similarity_threshold: 0.35  # 相似度阈值，低于此值过滤
```

**检索流程优化：**
```
请求 → 传 top_k=8 增大候选池
响应 → 按相似度得分降序排序
     → 过滤 < 0.35 的低相关 chunk
     → 日志记录过滤前后数量和每个 chunk 得分
```

#### 方案2：Query 改写

在 `search_medical_question.py` 中新增 `_optimize_rag_query()` 函数，利用 MedicalQwen 将口语化问题改写为检索友好的关键词形式：

```python
# 改写示例
"腹透要注意什么？"     → "腹膜透析 护理注意事项 饮食禁忌 并发症预防"
"我血压高能吃什么？"   → "腹膜透析 高血压 低盐饮食 钾磷控制"
"出口感染了怎么办？"   → "腹膜透析 导管出口感染 处理 消毒"
```

**数据流变更：**
```
修改前:
  user_query → search_from_ragflow(user_query) → MedicalQwen

修改后:
  user_query → _optimize_rag_query(user_query) → search_from_ragflow(optimized_query) → MedicalQwen
              └─ 失败时降级为原始 user_query
```

**涉及文件：** `plugins_func/functions/search_from_ragflow.py`、`plugins_func/functions/search_medical_question.py`、`config.yaml`

### 11.2 医疗入口预过滤器排除：体征数据上报/更新意图

**问题：** 患者询问体征数据上报与更新时（如"上报血压150/90"、"体重65公斤请上报"、"更新服药提醒"），医疗入口预过滤器因关键词"血压"、"体重"、"药"等命中而拦截，路由到 search_medical_question，而非对应的 submit_xxx_data 或 update_medication_reminder_status 插件。

**根本原因：**
`_is_medical_query()` 的关键词列表中有体征关键词（血压/血糖/体重/尿量/心率），但没有排除体征数据上报/更新意图的逻辑，导致所有包含这些关键词的查询都被强制路由到医疗大模型。

**解决方式：** 在 `_is_medical_query()` 中、医疗关键词匹配之前，新增两道排除逻辑：

#### 排除模式1：体征数据上报/记录/查询

当查询**同时包含**体征测量词和上报操作词时，判定为数据上报意图，不走医疗通道。

| 体征测量词 | 上报操作词 |
|-----------|-----------|
| 血压、血糖、体重、尿量、心率、高压、低压、收缩压、舒张压 | 上报、提交、登记、报上去、上交、提交一下、上报一下、帮我提交、帮我上报、反馈一下、记录、录入、保存、记下来、存一下、帮我记下、录入进去、保存一下、查询、查一下、查查、检索、查阅、调取、询查、核验、核对、浏览、查一查、看一看、找一找、帮我查下、翻一下、搜一下、看下记录 |

**处理流程：**
```python
has_reporting_verb = any(v in query for v in REPORTING_VERBS)
has_measurement = any(n in query for n in MEASUREMENT_NOUNS)
if has_reporting_verb and has_measurement:
    return False  # 放行给 LLM function_call
```

#### 排除模式2：服药提醒更新

当查询包含"更新" + "提醒/服药/用药提醒"时，排除不走医疗通道。

```python
if "更新" in query and ("提醒" in query or "服药" in query or "用药提醒" in query):
    return False  # 放行给 update_medication_reminder_status
```

#### 边界行为对照

| 用户输入 | 是否排除 | 预期路由 |
|---------|---------|---------|
| "上报血压150/90" | ✅ 排除 | `submit_blood_pressure_data` |
| "体重65公斤请上报" | ✅ 排除 | `submit_weight_data` |
| "记录血糖5.6" | ✅ 排除 | `submit_blood_glucose_data` |
| "更新服药提醒" | ✅ 排除 | `update_medication_reminder_status` |
| "血压高怎么办？" | ❌ 不排除 | `search_medical_question` ✅ |
| "血糖正常范围是多少" | ❌ 不排除 | `search_medical_question` ✅ |
| "我最近体重增加" | ❌ 不排除 | `search_medical_question` ✅ |

**涉及文件：** `core/connection.py`（仅修改 `_is_medical_query()` 方法）

### 11.5 知识库内容超长导致 MedicalQwen Token 超限 + 通用 LLM 压缩方案

**问题：** 当用户询问"腹透患者饮食注意事项"时，RAGFlow 返回了未经整理的杂乱长文本（知识库有输出），作为 MedicalQwen 的参考内容时，**总 prompt 达到 9052 tokens，超出模型上下文窗口（2048 tokens）**，API 直接返回 400 错误。

```
2026-06-11 14:17:49 [medical-gguf-api] ERROR
llama-server 流式错误: 400
{"error":{"code":400,"message":"request (9052 tokens) exceeds
the available context size (2048 tokens), try increasing it",
"type":"exceed_context_size_error","n_prompt_tokens":9052,"n_ctx":2048}}
```

**根本原因：**
1. RAGFlow 返回的知识库内容杂乱、未整理，且**未做长度控制**
2. MedicalQwen 通过 llama-server 部署，默认 `n_ctx=2048`，非常小
3. System prompt（~200 tokens）+ 知识库内容（~8800 tokens）+ 问题，远超限制
4. 失败路径同时存在 TTS 无声 Bug（错误消息未送到 TTS）

**解决方案（双层兜底）：**

#### 第1层：通用 LLM 智能压缩（`_compress_knowledge`）

在 `_query_knowledge_base()` 中，RAGFlow 检索之后、返回知识库内容之前，用通用 LLM 做一次摘要整理：

```python
def _compress_knowledge(conn, question, knowledge_text):
    """用通用LLM压缩知识库内容，使其简洁有序"""
    if not knowledge_text or len(knowledge_text) < 300:
        return ""  # 内容不长时跳过

    system_prompt = "你是一个医学知识整理助手。请将以下知识库内容压缩为简洁的摘要。"
    user_prompt = (
        f"要求：\n"
        f"1. 只保留与患者问题直接相关的信息\n"
        f"2. 合并重复和相似的内容\n"
        f"3. 按逻辑顺序整理（因→症→治）\n"
        f"4. 去除模糊和不确定的表述\n"
        f"5. 输出简洁连贯的段落，控制在500字以内\n\n"
        f"患者问题：{question}\n\n"
        f"知识库内容：\n{knowledge_text}\n\n"
        f"整理后的摘要："
    )
    compressed = conn.llm.response_no_stream(system_prompt, user_prompt)
    return compressed if compressed and len(compressed) >= 30 else ""
```

#### 第2层：硬截断兜底（`_call_medical_qwen`）

`_call_medical_qwen()` 中保留 1500 字符硬截断作为最终安全网：

```python
MAX_KNOWLEDGE_CHARS = 1500
if len(knowledge_context) > MAX_KNOWLEDGE_CHARS:
    knowledge_context = knowledge_context[:MAX_KNOWLEDGE_CHARS] \
        + "\n\n……（知识库内容过长，已截取相关度最高的部分）"
```

#### TTS 无声 Bug 修复

`_direct_medical_and_speak()` 中 MedicalQwen 失败时，错误消息只存入了 `conn.dialogue` 但未送到 TTS 播放，用户听到静音。修复：在 `Action.RESPONSE` 分支中手动调用 `tts_one_sentence`。

#### 完整数据流（当前）

```
用户问题
    │
    ▼
┌─ Step 0: 健康检查 ──────────────────────────────┐
│  GET {base}/health（5s超时，30s缓存）              │
│  → 健康 → 正常流水线                               │
│  → 不健康 → 降级路径（Level 1/2/3）               │
└──────────────────────────────────────────────────┘
    │
    ▼
┌─ Level 0 正常流水线 ────────────────────────────┐
│                                                  │
│  Stage 1: Query 改写 + RAGFlow 检索               │
│  MedicalQwen 改写口语化为关键词                    │
│  search_from_ragflow_v2 → 相似度+去重+截断        │
│  通用 LLM 压缩为 ~800 字摘要                       │
│    │                                              │
│  Stage 2: MedicalQwen 推理（段落输出）             │
│  system: 腹透健康助手                              │
│  user: 【KB参考内容】+【患者问题】                 │

│  → 回答结束后输出 ===END===                       │
│    │                                              │

│    │                                              │

│    │                                              │
│  Stage 5: 输出后处理（调用方）                     │
│  免责声明独立 TTS（暂停 1 秒后播报）               │

│                                                  │
├─ 降级路径（MedicalQwen 不可用） ──────────────────┤
│  Level 1: RAGFlow有结果 → 通用 LLM 基于 KB 回答   │
│  Level 2: RAGFlow无结果 → 通用 LLM 自身知识回答   │
│  Level 3: 通用 LLM 也失败 → "医疗系统繁忙"        │
```

#### 三层保障

| 层 | 位置 | 方法 | 效果 |

| 第1层 | `_compress_knowledge()` | 通用 LLM 智能压缩 | 9000→500 字符，保留关键信息 |
| 第2层 | `_call_medical_qwen()` | 1500 字符硬截断 | 压缩失败也不会 400 |
| 第3层 | llama-server 侧 | `--ctx-size 4096/8192` | 增大上下文（推荐同时调整） |

#### 安全性说明

`conn.llm.response_no_stream()` 直接调 LLM API 返回文本，**不走 function_call 路径**，不会触发 `search_medical_question` 递归调用。压缩失败时静默降级返回原始内容。

**涉及文件：** `plugins_func/functions/search_medical_question.py`、`core/handle/receiveAudioHandle.py`

### 11.6 知识库检索结果相关度提升

**问题：** 知识库检索返回的结果经常与患者问题相关度不高，即使经过 Query 改写和通用 LLM 压缩，如果 RAGFlow 召回的内容本身就不相关，后续的压缩和推理都会受影响。

**关键认知：** 检索质量的**天花板由 RAGFlow 知识库本身的文档结构、分块策略和 Embedding 模型决定**。代码层面的优化（Query 改写、相似度阈值过滤）只能缓解，不能根治。

**解决方案（按投入产出比从高到低）：**

#### 方案1：Chunk 分块策略优化（运营工作）

这是影响最大的单一因素。

| 策略 | 效果 | 说明 |
|------|------|------|
| ❌ 固定长度切分 | 差 | 一句话被截成两段，两段都检索不到 |
| ✅ 语义切分 | 好 | 按段落/标题自然边界切分，每个 chunk 语义完整 |
| ✅ Markdown/Header 层级切分 | 最好 | 按文档的 `##`、`###` 标题切分，层级关系保留 |

**建议值（在 RAGFlow 知识库设置中配置）：**
- Chunk 大小：500~800 tokens（中文场景偏大比偏小好）
- Chunk Overlap：128 tokens
- 切分方式：语义切分 或 Markdown 标题层级切分

#### 方案2：文档结构优化（运营工作）

在每个文档开头加一句摘要，向量检索时摘要与问题的语义匹配度更高：

```markdown
# 腹透患者饮食注意事项
> 摘要：本文介绍了腹透患者饮食中蛋白质、钾、磷的控制要点

### 蛋白质摄入
腹透患者每天蛋白质摄入量建议为 1.2-1.5g/kg 体重...
### 钾的控制
高钾食物包括香蕉、橙子、土豆...
```

**文档编写规范：**
- 每个知识点独立一个文件，避免大杂烩
- 每个文件开头写一句摘要
- 用 `##`、`###` 标题组织层级结构
- 一个文档只讲一个主题
- 清除页眉页脚、参考文献等无关内容

#### 方案3：配置 RAGFlow Rerank 模型（运维工作）

RAGFlow 内置重排序功能，向量检索先召回 top-20，rerank 模型再精排为 top-5，精度远高于纯向量排序。

在 RAGFlow 的 `service_conf.yaml` 中配置 rerank 模型：

```yaml
rerank_model: BAAI/bge-reranker-v2-m3
```

然后在 API 请求中启用：

```python
payload = {
    "question": question,
    "dataset_ids": dataset_ids,
    "top_k": 20,          # 增大召回池，给 rerank 更多候选
    "rerank": True,       # 启用 rerank
}
```

#### 方案4：更换 Embedding 模型（运维工作）

RAGFlow 使用的 Embedding 模型直接影响向量检索精度：

| 模型 | 适用场景 | 说明 |
|------|---------|------|
| `BAAI/bge-large-zh-v1.5` | 通用中文 | RAGFlow 默认，效果均衡 |
| `maidalun1020/bce-embedding-base_v1` | 中文 | 检索精度更高 |
| `shibing624/text2vec-base-chinese` | 中文医疗 | 对医学术语理解更好 |

在 RAGFlow 的 `.env` 中修改 `EMBEDDING_MODEL` 并重新向量化知识库。

#### 方案5：多 Query 检索（代码工作）

从多个角度生成检索 query，合并结果去重：

```python
def _multi_query_retrieval(conn, question):
    """生成多个角度的检索 query，合并结果"""
    queries = [
        _optimize_rag_query(conn, question),       # 关键词展开
        question,                                    # 原始问题
    ]
    all_chunks = []
    for q in queries:
        result = search_from_ragflow_v2(conn, question=q)
        if result.action == Action.REQLLM and result.result:
            all_chunks.append(result.result)
    # 合并去重（通过相似度判断）
    return merge_deduplicate(all_chunks)
```
