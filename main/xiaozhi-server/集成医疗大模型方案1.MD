# 医疗大模型（Qwen3.5-4B-Medical）+ RAGFlow 知识库 集成方案

> 基于 xiaozhi-esp32-server 现有架构，最小侵入式集成
> 知识库：RAGFlow（Docker 运行，已通过 `search_from_ragflow` 插件集成）
> 医疗 LLM：Qwen3.5-4B-Medical（外部项目 AutoTokenizer 部署，OpenAI 兼容接口）

---

## 一、整体架构

```
用户 → ASR → 文本
                │
                ▼
        通用LLM (function_call模式)
        工具列表: search_medical_question, get_weather, play_music ...
                │
       ┌────────┴────────┐
       ▼                 ▼
  LLM决定调 search_medical_question?   LLM直接回答
       │                  (闲聊/IoT/其他)
       ▼
  ┌────────────────────┐
  │  search_medical_question 插件    │
  │                     │
  │  1. RAGFlow 检索    │ ← search_from_ragflow (已存在)
  │                     │
  │  2. 构建医疗 Prompt  │
  │     system +        │
  │     知识库上下文 +   │
  │     用户问题        │
  │                     │
  │  3. 调 MedicalQwen  │ → POST http://localhost:8000/v1/chat/completions
  │     Provider        │ ← OpenAI 兼容接口
  │                     │
  │  4. 医疗内容校验     │
  └────────┬────────────┘
           │ (Action.REQLLM)
           ▼
      通用LLM 润色输出 → TTS
```

## 二、意图路由方案：纯 function_call（方案A）

最终采用 **纯 function_call 方案**，不引入前置分类器。

**理由：**
1. 项目已有 `TOOL_CALLING_RULES` 机制 + 深度 5 的递归兜底，抗偷懒机制成熟
2. `search_medical_question` 的工具描述写清楚触发条件后，通用 LLM 能准确判断
3. 腹透患者问题集中在特定领域（饮食/护理/体征/用药），LLM 容易识别
4. 前置分类器对"腹透"专精领域增益有限，但维护成本显著增加
5. 保持架构一致性：所有工具都通过 function_call 调度

## 四、各组件详细实现

### 4.1 MedicalQwen Provider

**路径：** `core/providers/llm/medical_qwen/medical_qwen.py`

```python
"""医疗Qwen3.5-4B-Medical Provider（OpenAI兼容接口）"""

from openai import OpenAI
from config.logger import setup_logging
from core.providers.llm.base import LLMProviderBase

TAG = __name__
logger = setup_logging()


class LLMProvider(LLMProviderBase):
    """
    医疗Qwen3.5-4B-Medical Provider
    对接外部项目通过 AutoTokenizer.from_pretrained 启动的服务
    接口格式：OpenAI 兼容 /v1/chat/completions
    """

    def __init__(self, config):
        self.model_name = config.get("model_name", "Qwen3.5-4B-Medical")
        self.base_url = config.get("base_url", "http://localhost:8000/v1")
        self.api_key = config.get("api_key", "not-needed")
        self.timeout = config.get("timeout", 60)

        self.client = OpenAI(
            api_key=self.api_key,
            base_url=self.base_url,
            timeout=self.timeout,
        )

    def response(self, session_id, dialogue, **kwargs):
        """流式响应"""
        try:
            stream = self.client.chat.completions.create(
                model=self.model_name,
                messages=dialogue,
                temperature=kwargs.get("temperature", 0.45),
                max_tokens=kwargs.get("max_tokens", 1024),
                top_p=kwargs.get("top_p", 0.9),
                repetition_penalty=kwargs.get("repetition_penalty", 1.1),
                stream=True,
            )
            for chunk in stream:
                if getattr(chunk, "choices", None):
                    delta = chunk.choices[0].delta
                    content = getattr(delta, "content", "") or ""
                    yield content
        except Exception as e:
            logger.bind(tag=TAG).error(f"MedicalQwen 流式响应失败: {e}")
            yield ""

    def response_no_stream(self, system_prompt, user_prompt, **kwargs):
        """非流式响应（供 search_medical_question 插件调用）"""
        dialogue = [
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": user_prompt},
        ]
        try:
            resp = self.client.chat.completions.create(
                model=self.model_name,
                messages=dialogue,
                temperature=kwargs.get("temperature", 0.45),
                max_tokens=kwargs.get("max_tokens", 1024),
                top_p=kwargs.get("top_p", 0.9),
                repetition_penalty=kwargs.get("repetition_penalty", 1.1),
                stream=False,
            )
            return resp.choices[0].message.content
        except Exception as e:
            logger.bind(tag=TAG).error(f"MedicalQwen 非流式响应失败: {e}")
            return ""
```

### 4.2 Medical QA 插件

**路径：** `plugins_func/functions/search_medical_question.py`

```python
"""
医疗问答插件
由通用LLM的function_call触发
流程: RAGFlow检索 → 医疗Qwen推理 → 内容校验 → 返回
"""
from plugins_func.register import register_function, ToolType, ActionResponse, Action
from plugins_func.functions.search_from_ragflow import search_from_ragflow
from config.logger import setup_logging
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from core.connection import ConnectionHandler

TAG = __name__
logger = setup_logging()

# 医疗QA工具描述
search_medical_question_FUNCTION_DESC = {
    "type": "function",
    "function": {
        "name": "search_medical_question",
        "description": "腹透患者医疗问答：当患者询问以下医疗健康问题时调用此工具获取专业回答："
                       "①饮食营养（吃什么、忌口、食谱、饮水量、蛋白质摄入）"
                       "②腹透护理（透析操作、管路护理、出口感染、并发症处理）"
                       "③体征咨询（血压、血糖、体重、尿量、水肿、超滤量）"
                       "④用药禁忌（药物相互作用、腹透相关用药注意事项）"
                       "非医疗问题（天气、新闻、音乐等）不要调用此工具",
        "parameters": {
            "type": "object",
            "properties": {
                "question": {
                    "type": "string",
                    "description": "患者提出的医疗相关问题原文"
                }
            },
            "required": ["question"]
        }
    }
}

# 医疗Qwen的system prompt
MEDICAL_SYSTEM_PROMPT = """你是一名专业的腹膜透析医疗健康助手。
约束条件：
1. 只回答用户当前提出的具体问题
2. 回答要简洁、准确、直接、控制在500字以内
3. 拒绝回答与腹透无关的问题"""


@register_function("search_medical_question", search_medical_question_FUNCTION_DESC, ToolType.SYSTEM_CTL)
def search_medical_question(conn: "ConnectionHandler", question=None):
    """
    医疗问答入口 — 被通用LLM的function_call触发

    Args:
        conn: 连接处理器
        question: 患者的医疗问题

    Returns:
        ActionResponse: REQLLM类型，结果交由通用LLM润色输出
    """
    if not question:
        return ActionResponse(Action.RESPONSE, None, "请告诉我您的医疗问题")

    logger.bind(tag=TAG).info(f"医疗问答触发，问题: {question}")

    # Step 1: 查询RAGFlow知识库
    knowledge_context = _query_knowledge_base(conn, question)

    # Step 2: 调用医疗Qwen推理
    medical_answer = _call_medical_qwen(conn, question, knowledge_context)

    # Step 3: 医疗内容安全校验
    medical_answer = _medical_verify(medical_answer)

    logger.bind(tag=TAG).info(f"医疗回答完成，长度: {len(medical_answer)}")

    # 返回给通用LLM做最终话术润色
    return ActionResponse(Action.REQLLM, medical_answer, None)


def _query_knowledge_base(conn, question):
    """查询RAGFlow知识库"""
    try:
        rag_result = search_from_ragflow(conn, question=question)
        if rag_result.action == Action.REQLLM and rag_result.result:
            logger.bind(tag=TAG).info(f"RAGFlow返回内容长度: {len(rag_result.result)}")
            return rag_result.result
    except Exception as e:
        logger.bind(tag=TAG).error(f"RAGFlow查询失败: {e}")

    return ""


def _call_medical_qwen(conn, question, knowledge_context):
    """调用医疗Qwen LLM"""
    from core.utils import llm as llm_utils

    medical_config = conn.config.get("LLM", {}).get("MedicalQwen")
    if not medical_config:
        logger.bind(tag=TAG).error("未找到MedicalQwen配置")
        return "医疗模型未配置，请联系管理员"

    medical_llm = llm_utils.create_instance("medical_qwen", medical_config)

    # 构建带知识库上下文的用户prompt
    if knowledge_context:
        user_prompt = f"""请基于以下知识库信息回答患者的医疗问题。

【知识库参考内容】
{knowledge_context}

【患者问题】
{question}"""
    else:
        user_prompt = question

    try:
        answer = medical_llm.response_no_stream(MEDICAL_SYSTEM_PROMPT, user_prompt)
        return answer.strip()
    except Exception as e:
        logger.bind(tag=TAG).error(f"医疗Qwen调用失败: {e}")
        if knowledge_context:
            return f"根据知识库信息：{knowledge_context[:200]}"
        return "医疗系统繁忙，请稍后再试"


def _medical_verify(text):
    """医疗内容安全校验"""
    if not text:
        return text

    # 禁忌词过滤/替换
    replacements = {
        "不限水": "遵医嘱控制饮水量",
        "随意饮水": "遵医嘱控制饮水量",
        "不用控制饮水": "遵医嘱控制饮水量",
    }
    for old, new in replacements.items():
        text = text.replace(old, new)

    # 追加免责声明（如未包含）
    disclaimer = "\n\n⚠️ 以上建议仅供参考，具体治疗方案请咨询您的主治医生。"
    if "医生" not in text and "咨询" not in text:
        text += disclaimer

    return text
```

## 八、优化迭代记录

### 8.1 问题：医疗大模型意图识别未触发（第一轮修复）

**现象：** 部署完成后，询问”腹透患者的饮食应该注意些什么时，通用 LLM 直接用自己的知识回答，没有触发 search_medical_question 工具。

**根因分析：**
1. `TOOL_CALLING_RULES` 中有”通用知识问答（非实时信息）→ 不调工具”的规则，LLM 认为医疗问答属于”通用知识问答”
2. `TOOL_CALLING_RULES` 只提到了 `search_from_ragflow`，没有提到 `search_medical_question`
3. 工具描述不够详细，LLM 无法将患者问题与工具描述准确关联

**修复方案（3层修复）：**

| 层次 | 修改文件 | 修复内容 |
|------|---------|---------|
| ① TOOL_CALLING_RULES | `connection.py` | 新增”医疗健康咨询必须调用 search_medical_question”规则，删除”通用知识问答不调工具”的误导规则 |
| ② 关键词预过滤器 | `connection.py` | 新增 `_is_medical_query()` 方法（30+ 腹透医疗关键词），命中后注入强制指令 |
| ③ 工具描述强化 | `search_medical_question.py` | 工具描述从简写扩展为详细覆盖，添加”腹膜炎、并发症”等关键词 |

---

### 8.2 问题：search_medical_question 触发不稳定，有时走通用LLM有时走知识库（第二轮修复）

**现象：** 第一轮修复后，询问”腹膜炎的并发症有哪些？”时，仍有时走通用LLM，有时走知识库（MedicalQwen 调用的降级路径），从不走医疗大模型。

**根因分析：**

**问题① — 路由不稳定的原因（时序竞争）：**
```
startToChat(conn, text)
  → handle_user_intent(conn, text)
     → if conn.intent_type == “function_call”: return False
     → 否则: analyze_intent_with_llm()
  → executor.submit(conn.chat, text)
```

`chat()` 中的预过滤器依赖 `self.intent_type == “function_call”` 和 `self.func_handler.has_tool(“search_medical_question”)`。

但 `_initialize_components()` 运行在线程池中，是异步初始化的：

```python
self.executor.submit(self._initialize_components)
```

如果第一条消息在初始化完成前到达，`intent_type` 仍为 `”nointent”`，预过滤器条件不满足，**整个预过滤器被跳过**，消息直接进入通用 LLM 处理。

**问题② — 知识库降级的原因（RAGFlow 正常、MedicalQwen 失败的路径）：**
```
search_medical_question 被触发
  → RAGFlow 查询成功（返回知识文本）
  → MedicalQwen 调用失败（连接被拒/超时）
  → 降级: 返回 “根据知识库信息：{截取前200字}”
```

用户配置的 `MedicalQwen base_url` 是 `http://localhost:8000/v1`，但实际服务跑在 `http://localhost:8101/v1`。

**最终修复方案（彻底解决）：**

核心思路：**将医疗拦截点从 `chat()` 内部移到消息入口 `startToChat()`，完全不依赖任何初始化状态。**

```
修改前（chat() 内部拦截）:
  startToChat → intentHandler → chat()
                                   ↓
                             医疗预过滤器
                      依赖 intent_type、func_handler 等
                      时序问题导致跳过 ❌

修改后（startToChat 入口拦截）:
  startToChat
     ↓
  医疗预过滤器 ← 这里拦截！零依赖！
     ↓
  _direct_medical_and_speak()
     ↓
  search_medical_question → RAGFlow → MedicalQwen → TTS
```

**具体变更：**

| 修改点 | 文件 | 说明 |
|--------|------|------|
| 新增入口拦截 | `core/handle/receiveAudioHandle.py:startToChat()` | 在 `handle_user_intent` 之前检查关键词，命中则直接路由 |

### 8.5 测试过程中发现的问题

**现象：** 当询问"腹膜炎的并发症有哪些？"时，有时触发了通用 LLM，有时触发了知识库（即 MedicalQwen 调用的降级路径），但**根本没有触发医疗大模型本身**。

**要求：** 询问任何与疾病有关的问题时，都走医疗大模型的路径，非医疗问题时走通用大模型。

#### 根因分析

**问题① — 路由不稳定的原因（时序竞争）：**

`chat()` 中的预过滤器依赖 `self.intent_type == "function_call"` 和 `self.func_handler.has_tool("search_medical_question")`。但 `_initialize_components()` 运行在线程池中（异步初始化）：

```python
self.executor.submit(self._initialize_components)
```

如果第一条消息在初始化完成前到达，`intent_type` 仍为 `"nointent"`，预过滤器条件不满足，**整个预过滤器被跳过**，消息直接进入通用 LLM 处理。

**问题② — 知识库降级的原因（RAGFlow 正常、MedicalQwen 失败的路径）：**

```
search_medical_question 被触发
  → RAGFlow 查询成功（返回知识文本）
  → MedicalQwen 调用失败（连接被拒/超时）
  → 降级：返回 "根据知识库信息：{截取前200字}"
```

用户配置的 `MedicalQwen base_url` 是 `http://localhost:8000/v1`，但实际服务跑在 `http://localhost:8101/v1`。

#### 最终修复方案（彻底解决）

核心思路：**将医疗拦截点从 `chat()` 内部移到消息入口 `startToChat()`，完全不依赖任何初始化状态。**

```
修改前（chat() 内部拦截）:
  startToChat → intentHandler → chat()
                                   ↓
                             医疗预过滤器
                      依赖 intent_type、func_handler 等
                      时序问题导致跳过 ❌

修改后（startToChat 入口拦截）:
  startToChat
     ↓
  医疗预过滤器 ← 这里拦截！零依赖！
     ↓
  _direct_medical_and_speak()
     ↓
  search_medical_question → RAGFlow → MedicalQwen → TTS
```

**具体变更：**

| 修改点 | 文件 | 说明 |
|--------|------|------|
| 新增入口拦截 | `core/handle/receiveAudioHandle.py:startToChat()` | 在 `handle_user_intent` 之前检查关键词，命中则直接路由 |
| 新增执行函数 | `core/handle/receiveAudioHandle.py:_direct_medical_and_speak()` | 在线程池中调用 search_medical_question 并输出 TTS |
| MedicalQwen 端口修正 | `config.yaml` | `base_url` 从 `localhost:8000` 改为 `localhost:8101` |

**修复后的数据流（医疗问题）：**

```
用户: "腹膜炎的并发症有哪些？"
  → startToChat() 入口
  → _is_medical_query("腹膜炎的并发症有哪些？")
     → 命中 "腹膜炎"、"并发症" ✅
  → 直接调用 _direct_medical_and_speak()
     → search_medical_question(conn, question=...)
        → RAGFlow 检索
        → MedicalQwen 推理 (localhost:8101)
        → 医疗校验
     → TTS 输出
  → return，完全不经过 intentHandler/chat()
```

**修复后的数据流（非医疗问题 — 不变）：**

```
用户: "今天天气怎么样？"
  → startToChat() 入口
  → _is_medical_query("今天天气怎么样？")
     → 未命中任何医疗关键词
  → handle_user_intent() → 通用LLM function_call → get_weather 工具
  → TTS 输出
```

**异常降级链（`_direct_medical_and_speak` 内部）：**

```
search_medical_question 调用
  ├── 成功 → Action.REQLLM → 直接输出医疗回答 → TTS
  ├── 失败 → Action.RESPONSE → 输出错误提示 → TTS
  └── 异常 → 输出"医疗系统繁忙，请稍后再试" → TTS
```

#### 与之前方案的本质区别

| 维度 | 之前（connection.py chat() 内） | 现在（startToChat 入口） |
|------|-------------------------------|------------------------|
| 拦截点 | chat() 内部，依赖很多条件 | startToChat，消息进系统第一站 |
| 条件依赖 | intent_type、func_handler、has_tool | 零依赖，只有关键词匹配 |
| 初始化时序 | 可能在初始化完成前失效 | 不依赖任何初始化 |
| 可靠性 | ❌ 时灵时不灵 | ✅ 100% 匹配命中 |
