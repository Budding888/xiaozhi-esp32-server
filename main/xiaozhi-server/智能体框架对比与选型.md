## 二、快速筛选（排除不适用的框架）

### 2.1 本项目核心约束

```
本项目作为纯CPU边缘部署的智能音箱后端服务，对智能体框架有明确约束:

🔴 必须满足 (否则不适用):
  1. 可嵌入现有Python项目 (非独立运行时)
  2. 兼容现有asyncio事件循环
  3. 能与现有@register_function插件系统集成
  4. 消息格式可适配现有WebSocket+TTS管道

🟡 强烈期望:
  5. 有管道编排能力 (RAG检索→LLM推理→融合→校验)
  6. 轻量 (纯CPU边缘部署, 内存敏感)
  7. 中文生态支持
```

### 2.2 快速排除结论

| 框架 | 排除结论 | 排除原因 |
|------|---------|---------|
| **Hermes Agent** | ❌ 排除 | 独立运行时(非库模式)，asyncio事件循环冲突，~200MB+太重，API不稳定(v0.x) |
| **LangGraph** | ❌ 排除 | 依赖LangChain全栈太重量，不适合纯CPU边缘部署，学习曲线陡峭 |
| **CrewAI** | ❌ 排除 | 角色扮演抽象层增加额外LLM开销，非必需的角色/任务/流程抽象 |

### 2.3 需深入评估的4个候选

```
✅ 进入深度评估:
  1. AgentScope 2.0     — 轻量可嵌入, 有管道编排, 中文生态完善
  2. OpenAI Agents SDK  — 极轻量(~800行), handoff机制, 但强OpenAI绑定
  3. pydantic-ai v2     — 类型安全优秀, 有Monty沙箱, 但多Agent能力弱
  4. smolagents          — 极轻(~1K行), 代码即行动, 但无管道编排
```

### 5.2 与现有 @register_function 插件的兼容性

```
本项目当前插件系统:
  @register_function(name, desc)  →  all_function_registry  →  UnifiedToolHandler
  已有20+函数: 天气/新闻/医疗/IoT/健康数据等

AgentScope 2.0:
  → ToolkitWrapper适配器
    class XiaozhiToolkitWrapper(Toolkit):
        def __init__(self, conn, function_names):
            for name in names:
                func_item = all_function_registry.get(name)
                tool = FunctionTool(name=name, func=wrapper, ...)
                self.tools.append(tool)
  ✅ 无需修改现有插件, 只需一层适配器
  ✅ 改造成本: 0（零代码改动）

smolagents:
  → 需要将每个 @register_function 重写为 @tool 格式
  → 需要删除原有的ActionResponse返回模式
  → 需要调整参数签名以支持类型提示
  ❌ 改造成本: 需重写20+函数 (中)

pydantic-ai v2:
  → 需要将每个函数重写为 @agent.tool 格式
  → 参数需要Pydantic model或类型注解
  ❌ 改造成本: 需重写20+函数 (中)

OpenAI Agents SDK:
  → 需要将每个函数重写为 @function_tool 格式
  → 参数从JSON schema改为函数签名
  ❌ 改造成本: 需重写20+函数 (中)

Hermes Agent (API模式):
  → 现有插件完全不变
  → Hermes进程独立运行, 不直接调用插件
  → 通过HTTP桥接器转发工具调用
  ✅ 改造成本: 低（仅需桥接层但增加HTTP延迟）
```

## 六、多智能体协作对比

| 维度 | AgentScope 2.0 | smolagents | pydantic-ai v2 | OpenAI Agents SDK | Hermes Agent |
|------|---------------|-----------|---------------|-------------------|-------------|
| **子Agent** | pipeline stage | ManagedAgent包装 | ❌ 无 | Handoff | spawn工具 |
| **协作模式** | Pipeline编排 | 主Agent→子Tool | ❌ 单Agent为主 | Agent→Agent handoff | 主→子 |
| **管道编排** | ✅ **sequential/fanout** | ❌ 无 | ⚠️ pydantic-graph(可选) | ✅ **Handoff链** | ❌ 无 |
| **消息广播** | ✅ **MsgHub** | ❌ 无 | ❌ 无 | ❌ 无 | ❌ 无 |
| **子Agent隔离** | ❌ 共享上下文 | ❌ 共享 | ❌ 共享 | ❌ 共享 | ✅ 独立会话 |
| **适用场景** | 医疗管道编排 | 单Agent任务 | 类型化单Agent | 代理间接力 | 并行子任务 |

**对本项目的影响**: 医疗问答需要 `RAG检索→MedicalQwen推理→融合→校验` 的多Stage编排。AgentScope 的 `sequential_pipeline` 原生支持这种流式管道；OpenAI Agents SDK 的 handoff 机制也能做链式处理但偏向代理间交接而非Stage编排；smolagents 和 pydantic-ai **完全没有管道编排**，需要自行手写 if/else 控制流——等于**没有解决现有架构的最大痛点**。

### 11.2 适配性结论

```
🔴 核心判断: AgentScope 2.0 是最适合本项目的智能体框架

核心理由:

1. 唯一解决核心痛点的框架
   现有架构的最大痛点是 chat() 深度递归 + 医疗管道 if/else 耦合。
   AgentScope 的 sequential_pipeline 直接解决此问题。
   其他框架 (smolagents / pydantic-ai) 无管道编排, 引入后等于没解决任何问题。

2. 唯一零成本兼容现有插件系统的框架
   通过 ToolkitWrapper 适配器, 现有 @register_function 函数无需任何修改。
   其他框架都需要将20+函数重写为各自的工具格式。

3. 唯一拥有完善中文生态的框架
   阿里巴巴通义实验室出品, 中文文档完善, 与国内云生态/模型API天然契合。
   音箱边缘部署场景, 中文生态支持直接影响运维效率。

4. "够用且刚好够用"的框架
   AgentScope 没有 Hermes 的冗重, 没有 smolagents 的过度简约,
   也没有 OpenAI SDK 的强供应商绑定。它提供了恰好满足本项目需求的能力。
```

### 12.4 pydantic-ai v2 集成方案（备选）

#### 集成方式: 库模式import + Capability组合

#### 优劣势
- ✅ 最强大的结构化输出(Pydantic天生), 医疗场景优势
- ✅ Monty Rust沙箱(~4.5MB), 极快代码执行
- ❌ 缺管道编排 → 需自行实现多stage流程 → 没解决核心痛点
- ❌ 缺多Agent协作 → 单Agent为主
- ❌ 需要重写20+插件函数为@agent.tool格式
- ❌ 需要pydantic-graph(可选)做状态机编排

### 12.5 smolagents 集成方案（备选）

#### 集成方式: 库模式import + CodeAgent

#### 优劣势
- ✅ 极轻(~1K行核心, ~20MB)
- ✅ 代码即行动(CodeAgent) → 复杂医疗推理场景更高效
- ❌ **最大问题: 无管道编排** → 等于没解决核心痛点
- ❌ CodeAgent不是异步的, run()是同步阻塞
- ❌ 需要重写20+插件函数为@tool格式
- ❌ 记忆/状态/持久化全无, 需自建

## 十三、最终选型建议

### 13.1 综合排序

```
🥇 推荐: AgentScope 2.0        — 96/120  管道+插件兼容+中文生态

🥈 可考虑: OpenAI Agents SDK   — 79/120  轻量+记忆+handoff, 但OpenAI绑定

🥉 不推荐当前选择:
   pydantic-ai v2             — 72/120  类型安全优秀, 但缺管道和多Agent
   smolagents                 — 65/120  极轻, 但缺管道和状态管理
   Hermes Agent               — 56/120  独立运行时, 无法嵌入
   LangGraph                  — 排除    太重, 不适合边缘CPU
   CrewAI                     — 排除    角色抽象不必要
```

### 13.2 为什么 AgentScope 2.0 仍然是最佳选择

| 理由 | 说明 |
|------|------|
| **解决核心痛点** | 管道编排直接解决医疗RAG→LLM→融合→校验的多Stage问题。其他框架或缺失(如smolagents)或需额外库(如pydantic-graph) |
| **零成本兼容** | ToolkitWrapper适配现有@register_function体系。其他框架都需要重写20+函数 |
| **asyncio原生** | 共享事件循环, 无冲突。CodeAgent(smolagents)是同步阻塞调用 |
| **中文生态** | 阿里通义出品, 与Qwen/DashScope/阿里云原生集成 |
| **恰好满足** | 没有Hermes的冗余, 没有smolagents的不足, 没有OpenAI的绑定 |

### 13.3 各框架定位总结

```
┌─────────────────────────────────────────────────────────┐
│              本项目智能体框架选型地图                        │
│                                                          │
│  如果你需要...                    → 选择...                │
│                                                          │
│  管道编排 + 现有插件零改动          → AgentScope 2.0       │
│  类型安全 + 结构化输出最强           → pydantic-ai v2       │
│  极轻量 + 代码执行Agent            → smolagents            │
│  OpenAI生态 + 官方SDK              → OpenAI Agents SDK    │
│  独立进程 + 跨会话记忆强            → Hermes Agent          │
│  复杂状态机 + HITL                → LangGraph              │
│  角色扮演多Agent团队               → CrewAI                 │
│                                                          │
└─────────────────────────────────────────────────────────┘
```

### 13.4 架构决策

| 决策 | 结论 | 依据 |
|------|------|------|
| **核心智能体框架** | AgentScope 2.0 | 管道编排+插件兼容+中文生态, 96/120 |
| **集成方式** | 方案A (Adapter/Wrapper) | 最低风险, legacy模式兜底 |
| **启用模式** | 默认legacy, 可选agentscope | 灰度验证, 可回退 |
| **跨会话记忆(后续)** | OpenAI Agents SDK SQLiteSession 或自研 | 当前非核心需求 |
| **结构化输出(可选)** | pydantic-ai v2 的Pydantic模型 | 可参考设计模式, 非直接依赖 |
